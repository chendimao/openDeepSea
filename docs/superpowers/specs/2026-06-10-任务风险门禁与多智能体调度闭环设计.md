# 任务风险门禁与多智能体调度闭环设计

## 背景

OpenDeepSea 已具备项目、会话、任务、工作流、ACP agent run、LangGraph runtime、全局智能体库和运行边界能力。当前需要把“用户发送一个问题后，系统自动判断任务类型并调度合适智能体完成闭环”的流程产品化：

1. 用户只需要表达目标。
2. 系统自动判断任务类型、风险等级和是否需要确认。
3. Planner 根据任务实际情况选择串行或并行流程，并分配给前端、后端、UI、测试、审查等智能体。
4. 子智能体执行过程中通过结构化事件向 Planner 汇报进度、阻塞和重大决策。
5. Planner 负责决策、重路由、返工和最终验收闭环。

本设计聚焦调度规则、风险门禁、通信协议和闭环状态机，不进入具体 UI 或数据库迁移实现。

## 社区方案借鉴

### LangGraph

LangGraph 的核心启发是将多智能体任务建模为显式状态图，而不是依赖自由群聊自然推进。状态图可以持久化、恢复、插入人工确认、按节点执行验证，并支持 review/repair loop。

借鉴点：

- graph state 是 workflow 的事实源。
- interrupt / human-in-the-loop 适合中高风险确认。
- evaluator-optimizer / review loop 适合测试失败后的返工。
- 事件流适合映射到 OpenDeepSea 时间线。

参考：

- https://docs.langchain.com/oss/javascript/langgraph/overview
- https://docs.langchain.com/oss/javascript/langgraph/persistence
- https://docs.langchain.com/oss/javascript/langgraph/interrupts
- https://docs.langchain.com/oss/javascript/langgraph/workflows-agents

### AutoGen

AutoGen 的 SelectorGroupChat 适合让模型动态选择下一个发言者，但它偏对话式，需要终止条件和轮次控制。GraphFlow 更适合正式开发任务，因为它用显式 execution graph 表达顺序、并行、条件分支和循环。

借鉴点：

- 群聊 UI 不应成为执行调度的事实源。
- speaker selection 可以由 LLM 建议，但执行顺序必须由 graph / scheduler 约束。
- execution graph 和 message visibility 应分离。

参考：

- https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html
- https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/graph-flow.html

### CrewAI

CrewAI 将 Agent、Task、Process 分开，Sequential / Hierarchical process 都强调 manager 或 process 控制任务推进。它适合作为角色分工参考，但 OpenDeepSea 需要更强的本地代码权限、写入范围、ACP run 和审计约束。

借鉴点：

- manager 负责 delegation 和 validation。
- agents 负责局部专业执行。
- process 比自由聊天更适合可重复的工程任务。

参考：

- https://docs.crewai.com/en/concepts/processes
- https://docs.crewai.com/en/concepts/collaboration

### OpenAI Agents SDK

OpenAI Agents SDK 将 handoff 表达为结构化 tool call，并通过 tracing 记录 generation、tool call、handoff、guardrail 等 span。它说明多智能体交接应成为结构化事件，而不是仅写在自然语言回复中。

借鉴点：

- handoff payload 必须结构化。
- tracing / span 可作为 OpenDeepSea agent run timeline 的设计参考。
- guardrail 适合映射为风险门禁和校验器。

参考：

- https://openai.github.io/openai-agents-python/handoffs/
- https://openai.github.io/openai-agents-python/tracing/

## 目标

1. 用户消息进入系统后，自动完成任务分类、风险判断和工作流选择。
2. 轻量任务自动执行；中高风险任务先展示计划、影响范围和验证方式，用户确认后执行。
3. Planner 作为控制平面，负责任务拆解、智能体分配、串并行决策、重大决策和返工调度。
4. 子智能体作为执行平面，必须通过结构化事件汇报进度、产物、阻塞和完成状态。
5. 测试、审查、返工、验收形成可恢复、可审计的闭环。
6. 并行开发必须受写入范围、依赖关系和共享 contract 约束。

## 非目标

- 不让智能体自由群聊直接驱动正式任务状态。
- 不让 Planner 直接修改代码或执行任意 shell。
- 不用自然语言声明伪造子智能体事件。
- 不在第一版做完全动态临时 workflow graph 执行。
- 不绕过现有 ACP adapter、workspace policy、agent run 和 workflow run 边界。

## 推荐架构

```text
User Message
  -> Intent Classifier
  -> Risk Gate
  -> Planner / Supervisor
  -> Typed Workflow Plan
  -> Approval Gate
  -> Scheduler / Dispatcher
  -> Agent Runs
  -> Review
  -> Verify
  -> Repair Decision
  -> Acceptance
  -> Memory / Summary
```

职责边界：

- **Intent Classifier**：判断轻量问答、bug 修复、前端、后端、全栈、头脑风暴、审查、纯信息问答等任务类型。
- **Risk Gate**：根据改动范围、权限、共享 contract、依赖、数据库、并行冲突等因素判定风险等级。
- **Planner / Supervisor**：生成 typed plan，决定串并行、agent assignment、验证方式和是否需要用户确认。
- **Scheduler / Dispatcher**：校验计划并创建 agent runs，保证运行边界、读写范围和依赖关系合法。
- **Executor Agents**：只处理分配给自己的局部任务。
- **Reviewer / Tester / Acceptor**：默认只读，负责审查、验证和验收。
- **Workflow Runtime**：持久化状态、恢复中断、记录事件、驱动 review/repair loop。

## 任务分类

建议第一版使用规则优先、LLM 补充的混合分类：

```ts
type TaskKind =
  | 'chat_answer'
  | 'brainstorming'
  | 'code_review'
  | 'bug_fix'
  | 'frontend_change'
  | 'backend_change'
  | 'fullstack_change'
  | 'test_only'
  | 'docs_only'
  | 'ops_or_config'
  | 'unknown';
```

分类输入：

- 用户消息。
- 当前会话上下文。
- 是否提到 bug、报错、测试失败、UI、API、数据库、配置、依赖、删除、重构。
- 项目内可用 agent、workflow definitions、默认验证命令。

分类输出必须结构化：

```ts
interface TaskClassification {
  kind: TaskKind;
  confidence: number;
  reason: string;
  suggestedWorkflow: string | null;
  requiresBrainstorming: boolean;
}
```

低置信度时，系统不应直接进入执行，而是降级到询问、头脑风暴或默认安全 workflow。

## 风险分级与确认门禁

### 轻量任务：自动执行

满足以下条件时可以自动执行：

- 单文件或小范围改动。
- 文案、样式、局部配置、小 bug、局部测试补充。
- 不涉及数据库 schema、依赖升级、权限、安全、CI、根配置。
- `scopeWrite` 明确且不与其他运行中任务冲突。
- 验证命令明确且低风险。

### 中风险任务：先确认

命中以下任一条件时先展示计划并等待用户确认：

- 前后端联动。
- 多模块或多文件改动。
- 修改 shared types、API contract、workflow 行为或任务状态机。
- 需要新增测试、改测试策略或引入 review/repair loop。
- 需要并行多个 agent 执行。
- 可能影响已有用户主流程。

### 高风险任务：必须确认

命中以下任一条件时必须确认，并在确认卡片中突出风险：

- 数据库迁移或数据清理。
- 依赖升级、构建系统、CI、根配置。
- 权限、安全、凭证、沙箱策略。
- 删除文件或大规模重构。
- 需要修改多个共享 contract / schema。
- 并行写入存在重叠风险。
- 需要执行潜在破坏性命令。

### 确认卡片

Planner 对中高风险任务输出确认卡片：

```ts
interface ApprovalCard {
  riskLevel: 'medium' | 'high';
  taskKind: TaskKind;
  summary: string;
  approvalReason: string;
  agents: string[];
  executionMode: 'serial' | 'parallel' | 'hybrid';
  scopeRead: string[];
  scopeWrite: string[];
  verification: Array<{
    command: string;
    reason: string;
    required: boolean;
  }>;
  risks: string[];
  assumptions: string[];
}
```

用户确认前，Scheduler 不创建执行型 agent run。

## Typed Workflow Plan

Planner 输出必须通过 schema 校验：

```ts
interface AgentWorkflowPlan {
  goal: string;
  taskKind: TaskKind;
  riskLevel: 'low' | 'medium' | 'high';
  requiresApproval: boolean;
  executionMode: 'serial' | 'parallel' | 'hybrid';
  assumptions: string[];
  steps: AgentWorkflowStep[];
  verification: VerificationCommand[];
  maxRepairAttempts: number;
}

interface AgentWorkflowStep {
  id: string;
  title: string;
  stage: 'analysis' | 'implementation' | 'review' | 'verification' | 'acceptance' | 'summary';
  assigneeRole: 'planner' | 'frontend_executor' | 'backend_executor' | 'ui_designer' | 'tester' | 'reviewer' | 'acceptor';
  requiredCapabilities: string[];
  scopeRead: string[];
  scopeWrite: string[];
  dependsOn: string[];
  canRunInParallel: boolean;
  acceptance: string[];
}
```

校验规则：

- `scopeWrite` 不能为空泛化为整个项目，除非用户明确确认高风险。
- 需要改 shared contract、schema、根配置或依赖时，`requiresApproval` 必须为 `true`。
- 没有合适 agent 时，计划必须进入 `blocked` 或请求用户配置 agent。
- 验证命令必须走 allowlist 或人工确认。

## 串并行调度规则

默认串行，满足以下条件才允许并行：

1. 任务之间没有依赖关系。
2. `scopeWrite` 不重叠。
3. 不修改同一个 shared contract、schema、root config、lockfile 或应用入口。
4. 每个任务都有独立可验证的完成标准。
5. 对应 agent 不处于 busy 状态，且 workspace policy 覆盖写入范围。

禁止并行的默认场景：

- 同时修改 `package.json`、lockfile、CI、数据库迁移。
- 同时修改 shared types / API contract。
- 根因未明的 bug 修复。
- 需要先确定产品决策或架构决策。
- 拆分后整合成本明显高于收益。

## Planner 与子智能体通信协议

子智能体必须通过结构化事件和 Planner 通信，不能只在正文中声明状态。

```ts
type AgentEventType =
  | 'started'
  | 'progress'
  | 'artifact'
  | 'decision_request'
  | 'scope_change_request'
  | 'blocked'
  | 'completed'
  | 'failed';

interface AgentEvent {
  workflowRunId: string;
  stepId: string;
  agentRunId: string;
  type: AgentEventType;
  summary: string;
  detail?: string;
  progress?: number;
  artifacts?: string[];
  requestedDecision?: {
    question: string;
    options?: string[];
    recommendation?: string;
    impact: string;
  };
}
```

Planner 可回传以下命令：

```ts
type PlannerCommandType =
  | 'continue'
  | 'revise'
  | 'split_task'
  | 'reroute'
  | 'request_user_approval'
  | 'stop';

interface PlannerCommand {
  workflowRunId: string;
  stepId: string;
  targetAgentRunId: string | null;
  type: PlannerCommandType;
  reason: string;
  payload?: unknown;
}
```

子智能体遇到以下情况必须向 Planner 发起 `decision_request` 或 `scope_change_request`：

- 需要修改 `scopeWrite` 外文件。
- 发现计划拆分错误或依赖缺失。
- 需要修改 shared contract、schema、根配置、依赖或 CI。
- 并行任务出现写入冲突。
- 测试失败且根因超出自身任务边界。
- 需要用户做产品、视觉或架构决策。
- 原计划验证方式不可执行。

## 闭环状态机

```text
classify
  -> plan
  -> approval_gate
  -> dispatch
  -> execute
  -> review
  -> verify
  -> repair_decision
      -> execute
      -> acceptance
  -> memory
  -> completed
```

状态说明：

- `classify`：识别任务类型与风险等级。
- `plan`：生成 typed workflow plan。
- `approval_gate`：轻量任务直接通过，中高风险等待确认。
- `dispatch`：选择 agent，创建 workflow steps 和 agent runs。
- `execute`：执行实现任务，收集结构化事件。
- `review`：Reviewer 审查代码、行为、边界和风险。
- `verify`：Tester 或系统执行 allowlist 验证命令。
- `repair_decision`：失败时生成 repair task 并回到对应 executor。
- `acceptance`：Acceptor 对照用户目标和验收标准做最终判断。
- `memory`：记录任务总结、关键决策、踩坑和验证结果。

返工限制：

- 每个 workflow 默认最多 `maxRepairAttempts = 2`。
- 超过次数后进入 `blocked`，并展示失败原因、最近修复摘要和建议下一步。
- 高风险任务返工后如扩大范围，必须重新进入确认门禁。

## 数据落点建议

第一阶段优先复用现有数据模型：

- `workflow_runs.graph_state`：保存完整状态图快照。
- `workflow_steps`：保存步骤、阶段、agent assignment、状态。
- `agent_runs`：保存每次 ACP agent 执行。
- `task_events` 或现有 timeline 投影：保存结构化 agent events。
- artifact / message metadata：保存计划、确认卡片、验证结果、review findings。

如后续查询压力上升，再拆分专门表：

- `workflow_agent_events`
- `workflow_approval_cards`
- `workflow_repair_attempts`
- `agent_run_links`

## UI 展示建议

第一版 UI 只需要展示关键可解释性：

- 任务分类结果和风险等级。
- 轻量任务自动执行标识。
- 中高风险确认卡片。
- 当前执行模式：串行 / 并行 / 混合。
- 每个步骤的 agent、状态、进度、读写范围。
- 子智能体结构化事件。
- review findings、verification results、repair attempts。
- 最终验收摘要和已写入记忆。

UI 不应根据自然语言猜测真实子智能体状态，只展示结构化事件和 agent run 事实。

## 错误处理

- 分类失败：降级为默认安全 workflow 或请求用户澄清。
- Planner 输出非法：重试一次；仍失败则 blocked。
- 无可用 agent：请求用户添加或启用 agent。
- Agent 越权请求：Planner 拒绝并要求重新规划，必要时请求用户确认。
- 验证命令不在 allowlist：进入确认门禁。
- 子智能体失联或 ACP run 失败：记录失败事件，按 retry / repair 策略处理。
- 并行冲突：暂停冲突任务，Planner 重新排序为串行。

## 验收标准

1. 轻量任务可以无需确认自动进入执行，并在完成后展示验证结果。
2. 中高风险任务在执行前展示确认卡片，用户确认后才创建执行型 agent run。
3. Planner 输出的计划包含任务类型、风险等级、串并行模式、步骤、读写范围和验证命令。
4. Scheduler 拒绝不合法写入范围、非法 agent assignment 和危险验证命令。
5. 子智能体可以通过结构化事件向 Planner 报告进度、阻塞、重大决策和完成状态。
6. Review 或验证失败后，系统能生成 repair task 并回到对应 executor。
7. 超过最大返工次数后 workflow 进入 blocked，并给出失败摘要和下一步建议。
8. UI 时间线只展示真实结构化事件，不把自然语言声明当作子智能体执行事实。

## 推荐推进顺序

1. 实现任务分类与风险分级 schema。
2. 扩展 Planner 输出 typed workflow plan 和 approval card。
3. 增加 approval gate：轻量自动，中高风险等待确认。
4. 增加结构化 agent event 协议和 timeline 投影。
5. 强化 Scheduler 的串并行准入和写入冲突检查。
6. 接入 review / verify / repair loop。
7. 补充 UI 确认卡片和执行树展示。
8. 完成端到端 fake agent workflow 测试。

- MVP 实施覆盖任务分类、风险门禁、确认卡片、结构化 agent event、并行调度守卫、review/verify 返工上限和前端 timeline 展示。
- 第一阶段未新增数据库表，结构化数据优先落在 graph state、artifact metadata 和 task event metadata。
