# AI 模型配置中心设计

## 背景

当前系统设置中的 `model` 分类主要管理 OpenAI-compatible 的 planner 配置，后端对应 `settingsRepo` 的 `ai_configs` 与 `active_ai_config_id`。ACP provider 的运行配置仍分散在适配器中：

- Codex 与 Claude Code 默认依赖各自 CLI 的全局配置，运行时不显式传模型。
- OpenCode 当前在适配器中使用 `OPENCLAW_OPENCODE_MODEL || DEFAULT_OPENCODE_MODEL`，与其他 provider 行为不一致。
- 系统设置无法展示本机 Codex / Claude Code / OpenCode 的全局配置状态，也无法让用户知道一次运行最终使用了哪个模型来源。

本设计将系统设置的 AI / 模型模块重构为 Provider 配置中心，让 OpenDeepSea 可以在启动后只读发现本机 CLI 全局配置，同时用托管 profile 明确控制运行时模型覆盖。

## 已确认边界

1. 采用“只读导入 + 托管覆盖”。
2. OpenDeepSea 不写回 `~/.codex`、`~/.claude`、`~/.config/opencode` 或用户手动选择的 CLI 配置目录。
3. 启动自动扫描只更新发现快照，不直接改写实际运行的托管 profile。
4. 用户可关闭自动扫描；关闭后启动不再自动读取和更新 Codex / Claude Code / OpenCode 全局配置。
5. 用户可手动同步全部 provider，也可单独同步某个 provider。
6. 每个 CLI provider 都可以手动选择配置目录，并可恢复默认目录。

## 信息架构

系统设置中的 `AI & Models` 分类调整为 Provider 配置中心，保留现有设置弹窗结构，新增四个区域。

### 同步策略

顶部展示全局同步控制：

- 自动扫描全局配置：控制 backend 启动后是否后台同步三个 provider。
- 全部手动同步：立即读取所有 provider 的配置目录并更新发现快照。
- 最近同步摘要：显示最后同步时间、成功数量、失败数量。

### Provider 状态卡片

三张 provider 卡片分别展示 Codex、Claude Code、OpenCode：

- CLI 是否可用。
- 当前配置目录。
- 是否使用默认目录。
- 配置文件是否找到。
- 最近同步时间与同步状态。
- 发现模型、base URL、API key 是否存在和脱敏预览。
- 托管覆盖是否启用。

每张卡提供：

- 选择配置目录。
- 恢复默认目录。
- 单独手动同步。
- 从发现快照导入或更新托管 profile。

默认目录：

- Codex：`~/.codex`
- Claude Code：`~/.claude`
- OpenCode：`~/.config/opencode`

### 托管 Profile 列表与编辑

OpenDeepSea 保存自己的 provider profile。profile 可以来自本机发现快照，也可以由用户手动创建或编辑。

字段包括：

- provider。
- profile 名称。
- model。
- base URL。
- API key。
- reasoning effort。
- 是否启用运行覆盖。
- 是否为该 provider 的 active profile。

API key 只在写入时接收原文；读取时只返回是否已设置和脱敏预览。

### 运行解析摘要

设置页底部展示当前运行解析结果，让用户能看到最终来源：

1. 当前 Agent / Project / Room 决定 provider。
2. provider active managed profile。
3. discovered snapshot fallback。
4. provider CLI 自身默认行为。

## 数据模型

新增三类数据，不复用现有 `ai_configs`，避免混淆 planner OpenAI-compatible 配置与 ACP CLI 运行配置。

### Provider Source

记录 provider 的配置目录和同步策略。

```ts
interface ProviderConfigSource {
  provider: AcpBackend;
  config_dir: string | null;
  use_default_config_dir: boolean;
  auto_sync_enabled: boolean;
  last_sync_at: number | null;
  last_sync_status: 'idle' | 'success' | 'failed';
  last_sync_error: string | null;
  updated_at: number;
}
```

语义：

- `use_default_config_dir = true` 时，backend 使用该 provider 的默认目录。
- `use_default_config_dir = false` 时，backend 使用用户选择的 `config_dir`。
- `auto_sync_enabled` 可先做 provider 级；UI 顶部的全局开关批量设置三个 provider。

### Discovered Snapshot

记录只读扫描得到的规范化结果。自动同步和手动同步只更新它，不直接影响运行 profile。

```ts
interface ProviderDiscoveredSnapshot {
  provider: AcpBackend;
  config_dir: string;
  config_file: string | null;
  detected_model: string | null;
  detected_base_url: string | null;
  api_key_set: boolean;
  api_key_preview: string | null;
  reasoning_effort: string | null;
  raw_summary_json: string;
  synced_at: number;
}
```

`raw_summary_json` 只保存脱敏摘要，不保存原始密钥。不同 CLI 的配置结构差异较大，因此解析器输出规范化字段，同时保留有限摘要用于 UI 解释。

### Managed Provider Profile

OpenDeepSea 真正用于运行时覆盖的配置。

```ts
interface ManagedProviderProfile {
  id: string;
  name: string;
  provider: AcpBackend;
  model: string | null;
  base_url: string | null;
  api_key: string | null;
  reasoning_effort: string | null;
  run_overrides_enabled: boolean;
  is_active: boolean;
  created_from_snapshot_at: number | null;
  created_at: number;
  updated_at: number;
}
```

约束：

- 每个 provider 最多一个 active profile。
- 删除 active profile 后，该 provider 回退到 discovered snapshot 或 CLI 默认行为。
- 从发现快照导入时，只有用户显式触发才写入或更新 managed profile。

## 同步流程

### 启动自动同步

backend 启动并开始监听后，后台触发 provider 配置同步：

1. 读取三个 provider 的 source 配置。
2. 对 `auto_sync_enabled = true` 的 provider 解析配置目录。
3. 更新 discovered snapshot 和 source 的 `last_sync_*` 字段。
4. 失败不阻塞 backend 启动，只记录错误并在 UI 展示。

### 手动同步

手动同步分两类：

- 同步全部 provider。
- 同步单个 provider。

同步只更新 discovered snapshot。用户如果希望运行配置跟随发现值，需要点击“从发现值导入/更新 profile”。

### 目录选择

用户可为每个 provider 选择配置目录。目录选择更新 source：

- 选择目录后：`use_default_config_dir = false`，`config_dir = selectedPath`。
- 恢复默认目录后：`use_default_config_dir = true`，`config_dir = null`。

自动同步和手动同步都以 source 解析出的最终目录为准。

## 配置解析

解析器按 provider 分离实现：

- Codex：读取 `config.toml`，解析 `model_provider`、`model`、`model_reasoning_effort`、对应 provider 的 `base_url`、密钥状态。
- Claude Code：读取 `settings.json` 与相关环境配置摘要，解析 `ANTHROPIC_MODEL`、`ANTHROPIC_BASE_URL`、默认模型变量和 reasoning 信息。
- OpenCode：读取 `opencode.json`，解析顶层 `model`、provider base URL、provider apiKey、reasoning 设置。

解析器必须脱敏：

- 不向 API 返回原始 key。
- 不在 `raw_summary_json` 保存原始 key。
- 预览仅使用固定格式，例如 `sk-...1234` 或 `...1234`。

## 运行时解析

ACP 运行时按 provider 解析配置：

1. 现有 Agent / Project / Room 逻辑决定 provider。
2. 查询该 provider 的 active managed profile。
3. 如果 active profile 存在且 `run_overrides_enabled = true`，运行适配器显式注入配置。
4. 如果没有 active profile 或未启用覆盖，则可 fallback 到 discovered snapshot。
5. 如果 snapshot 没有可用模型，则使用 provider CLI 自身默认行为。

适配器调整方向：

- Codex：支持从 resolved provider runtime config 注入 model、reasoning effort、base URL 或相关环境变量；保留现有 CLI 默认行为作为 fallback。
- Claude Code：支持用环境变量覆盖 `ANTHROPIC_MODEL`、`ANTHROPIC_BASE_URL` 等；保留 CLI 默认行为作为 fallback。
- OpenCode：移除“代码内硬编码默认模型作为首选”的行为，优先使用 resolved provider runtime config，再 fallback 到环境变量和 CLI 默认值。

## API 设计

新增 provider config API：

```txt
GET  /api/settings/provider-configs
PATCH /api/settings/provider-configs/:provider/source
POST /api/settings/provider-configs/:provider/sync
POST /api/settings/provider-configs/sync
POST /api/settings/provider-configs/:provider/import-profile
POST /api/settings/provider-profiles
PATCH /api/settings/provider-profiles/:id
POST /api/settings/provider-profiles/:id/activate
DELETE /api/settings/provider-profiles/:id
```

响应应包含：

- provider source。
- discovered snapshot。
- provider profiles。
- 每个 provider 的 effective runtime summary。

目录选择可复用现有 `/api/system/pick-directory` 能力，前端拿到路径后调用 source patch API。

## 错误处理

- 配置目录不存在：source 状态标记为 `failed`，错误为 `missing_dir`，不清空旧 snapshot。
- 配置文件不存在：标记为 `missing_config`，允许继续使用托管 profile。
- 文件解析失败：记录解析错误，保留旧 snapshot。
- 自动同步失败：不阻塞启动，不影响已有 active profile。
- API key 缺失：允许保存 profile，但运行摘要标记为可能依赖 CLI 自身认证或运行失败。
- provider 不支持某字段：字段保留在 profile，但 runtime summary 标记为未注入或不适用。

## 与现有系统的关系

- 保留现有 `ai_configs` 用于 LangChain planner / OpenAI-compatible 模型。
- 新增 provider profile 专门用于 ACP CLI provider 运行。
- `session_planner_acp_backend` 仍负责选择 planner 使用哪个 ACP provider，不负责配置具体模型。
- Agent 的 `default_acp_backend` 与权限模式保持现有语义。

## 验证范围

后端测试：

- provider source 默认目录与手动目录解析。
- 自动同步开关。
- 手动同步单 provider 和全部 provider。
- 配置文件缺失、目录缺失、解析失败时保留旧 snapshot。
- API key 脱敏。
- 每个 provider 只能有一个 active profile。

ACP adapter 测试：

- Codex 能按 active profile 注入模型和 reasoning。
- Claude Code 能按 active profile 注入环境变量。
- OpenCode 优先使用 resolved runtime config，不再把硬编码默认模型作为首选。
- 无 profile 时保留 CLI 默认 fallback。

前端测试：

- 系统设置展示同步策略、provider 卡片、目录选择、同步状态。
- profile 创建、编辑、激活、删除、从 snapshot 导入。
- 错误状态和运行解析摘要展示。

最终验证：

- 运行与本次改动直接相关的测试。
- 运行 `npm run build` 作为最低门禁。

## 非目标

- 不把 provider profile 写回 CLI 原始配置文件。
- 不重构 Agent / Project / Room 的 provider 选择逻辑。
- 不移除现有 planner `ai_configs`。
- 不实现跨机器或云端同步。
