# Electron 无边框窗口与内嵌窗口控制设计

## 背景

Electron 可安装 MVP 当前使用系统原生标题栏。这个标题栏与 OpenDeepSea 自己的顶部栏并存，会形成一层通用的顶部外边框，使桌面版看起来像“网页装进窗口”，而不是一个完整的本地客户端。

本设计将 Electron 版窗口改为无边框窗口，并把关闭、最小化、最大化/还原控件内嵌到现有应用顶部栏中。Web 端保持现状，不引入桌面窗口控制。

## 目标

- Electron 版去掉系统原生标题栏和通用顶部外边框。
- 最小化、最大化/还原、关闭按钮由应用 UI 提供。
- 窗口按钮位置遵循平台习惯：macOS 左侧，Windows/Linux 右侧。
- 顶部栏可拖拽窗口，导航、菜单、设置、通知和窗口按钮仍可正常点击。
- Web 端和未来远程 Web 模式不显示窗口控制，不依赖 Electron API。

## 非目标

- 不重做整个顶部栏信息架构。
- 不改变现有导航、设置、通知、菜单的业务逻辑。
- 不实现系统级自定义菜单栏、托盘、全屏沉浸模式或自动更新能力。
- 不把窗口控制暴露给后端 HTTP API。
- 不在 Web 浏览器中模拟桌面窗口按钮。

## 推荐方案

采用 Electron-only frameless shell。

Electron main 进程创建主窗口时启用无边框窗口。preload 通过 `contextBridge` 在既有 `window.openDeepSeaDesktop` 对象上暴露最小窗口控制 API。前端 `AppShell` 检测该 API 是否存在，只在 Electron 环境渲染 `DesktopWindowControls`。

窗口按钮按平台分区渲染：

- macOS：放在顶部栏左侧，位于品牌 logo 之前。
- Windows/Linux：放在顶部栏右侧，位于现有操作区之后。

顶部栏整体作为拖拽区域，所有交互控件显式声明为不可拖拽区域，避免 Electron 抢占点击事件。

## 备选方案与取舍

### 方案 A：Electron 无边框窗口，应用内窗口控件

优点：

- 视觉上最符合“桌面客户端”目标。
- 可复用现有顶部栏，不需要新增一层壳。
- Web 端可通过 Electron API 检测完全隔离。
- 后续可继续扩展窗口状态、全屏、平台菜单等能力。

缺点：

- 需要处理拖拽区与按钮点击区的 Electron 细节。
- 不同平台的窗口控件位置、hover 样式和最大化状态需要明确测试。

这是本次推荐方案。

### 方案 B：保留系统标题栏，只调整窗口背景和顶部间距

优点：

- 实现风险最低。
- 使用系统标题栏，窗口行为天然可靠。

缺点：

- 无法去掉用户指出的通用顶部外边框。
- 桌面版仍然缺少产品一体感。
- 与本次目标不匹配。

### 方案 C：使用 Electron titleBarOverlay

优点：

- 可以保留部分系统窗口行为。
- 在部分平台上接近原生外观。

缺点：

- 平台差异明显，Linux 支持和表现不稳定。
- 控件布局与现有 React 顶部栏耦合更难控制。
- 对 MVP 来说调试成本高于收益。

## 架构设计

### Electron main

`packages/desktop/src/main.ts` 负责：

- 创建 `BrowserWindow` 时启用无边框窗口。
- 监听窗口最大化、还原、全屏等状态变化。
- 注册窗口控制 IPC：
  - 最小化窗口。
  - 最大化或还原窗口。
  - 关闭窗口。
  - 查询当前窗口状态。
  - 可选地向 renderer 推送窗口状态变化。

窗口控制只作用于发起 IPC 的当前窗口，不影响后端 sidecar、数据目录或其他桌面能力。

### Preload

`packages/desktop/src/preload.ts` 在现有 `window.openDeepSeaDesktop` 上补充桌面窗口 API：

- `platform`
- `minimizeWindow()`
- `toggleMaximizeWindow()`
- `closeWindow()`
- `getWindowState()`
- `onWindowStateChanged(listener)`

`platform` 使用 Node/Electron 的平台值，例如 `darwin`、`win32`、`linux`。窗口状态 API 返回最小状态对象，例如是否最大化、是否全屏。前端只依赖这些语义，不直接引用 Electron 模块。

### Frontend AppShell

`packages/frontend/src/components/AppShell.tsx` 新增 `DesktopWindowControls`：

- 仅当 `window.openDeepSeaDesktop` 存在且包含窗口控制方法时渲染。
- macOS 左侧渲染，Windows/Linux 右侧渲染。
- 最大化按钮根据窗口状态切换图标与 aria-label。
- 所有按钮使用现有 icon button 尺寸和 focus 样式，保持顶部栏高度不变。

前端通过 preload 暴露的 `platform` 判断布局位置。若平台字段不可用，默认按 Windows/Linux 右侧处理，避免在非 macOS 平台把控件放错到左侧。

## UI 设计

内嵌窗口控制作为顶部栏的一部分，而不是新增独立标题栏。

视觉原则：

- 控件紧凑，使用图标按钮，不使用大面积文字按钮。
- 默认状态低干扰，hover/focus 时提供明确反馈。
- 关闭按钮在 Windows/Linux 右侧 hover 时使用危险色反馈；macOS 左侧也可以保持克制的危险色反馈，但不强行复刻系统红黄绿圆点。
- 顶部栏高度、logo 对齐、导航位置保持稳定，不因按钮出现产生跳动。

交互原则：

- 点击最小化后窗口进入系统最小化状态。
- 点击最大化按钮时在最大化和还原之间切换。
- 点击关闭时走当前 Electron 应用退出流程，不额外弹出确认。
- 双击顶部栏是否触发最大化不作为本期硬要求；如果现有 Electron 平台默认没有该行为，本期不额外实现。

## 拖拽与点击规则

CSS 需要明确划分拖拽区域：

- `.deepsea-topbar` 或 Electron 专用顶部栏容器设置 `-webkit-app-region: drag`。
- 所有可交互元素设置 `-webkit-app-region: no-drag`。
- 需要覆盖的元素包括导航链接、菜单按钮、设置按钮、通知按钮、窗口控制按钮、输入框、下拉菜单触发器。

这条规则是本功能的关键验收点。窗口可以拖动，但顶部栏中的按钮不能被拖拽区域吞掉点击事件。

## 平台行为

### macOS

- 无边框窗口按钮放在左侧。
- 左侧按钮与品牌 logo 保持间距，避免误触。
- 保留顶部栏可拖拽能力。

### Windows/Linux

- 无边框窗口按钮放在右侧。
- 顺序为最小化、最大化/还原、关闭。
- 关闭按钮 hover 使用更强的危险色反馈，符合 Windows 用户预期。

## 错误处理

- 如果 preload API 不存在，前端不渲染窗口控制。
- 如果某个窗口控制 IPC 调用失败，前端不展示阻塞式错误弹窗，保留控制台错误即可。
- 如果窗口状态订阅不可用，最大化按钮仍可调用 toggle，图标可以使用默认最大化状态。
- Web 端不应因为缺少 `window.openDeepSeaDesktop` 抛错。

## 测试与验证

最低验证：

- `packages/frontend/src/components/AppShell.test.tsx` 覆盖 Electron API 存在时显示窗口控制、Web 环境隐藏窗口控制。
- 覆盖 macOS 与 Windows/Linux 的按钮位置分支。
- 覆盖最大化状态下 aria-label 或图标状态变化。
- `npm run build -w @openclaw-room/frontend`
- `npm run build -w @openclaw-room/desktop`

手动 smoke：

- Electron dev 模式打开后没有系统标题栏。
- 顶部栏空白区域可以拖动窗口。
- 导航、设置、通知、菜单仍可点击。
- 最小化、最大化/还原、关闭按钮可用。
- macOS 按钮在左侧，Windows/Linux 按钮在右侧。

## 验收标准

- Electron 版窗口不再显示系统原生顶部标题栏。
- 应用顶部栏内显示平台位置正确的窗口控制。
- Web 浏览器访问时不显示窗口控制。
- 顶部栏可拖动窗口，交互控件点击不受影响。
- 最大化/还原状态能被前端正确表达。
- 桌面端构建通过，现有 Web 端构建不回退。

## 风险

- 无边框窗口会让拖拽区域和点击区域变成前端责任，CSS 漏标 `no-drag` 时容易出现按钮失效。
- macOS、Windows、Linux 的无边框表现存在平台差异，需要至少在当前开发平台做真实 Electron smoke。
- 如果顶部栏后续新增交互控件，需要同步加入 `no-drag` 规则。
- 不做原生标题栏后，系统级窗口菜单和平台快捷行为需要依赖 Electron 默认能力或后续单独补齐。
