# 知识库 Phase 3 知识沉淀设计

- 日期：2026-06-08
- 来源设计：`docs/superpowers/specs/2026-06-07-资源页升级知识库设计.md`
- 前置状态：
  - Phase 1 已完成知识库页面、基础解析、FTS、详情、显式引用。
  - Phase 2 已完成 `openclaw:knowledge` Agent RAG 工具、citation 和 usage refs。
- 实施范围：会话和智能体产物沉淀到项目知识库的最小闭环。

## 1. 目标

Phase 3 让用户可以把 Session 中的结论、决策和经验沉淀为可检索知识，而不是只留在会话消息里。

本阶段必须完成：

1. 从 Session 消息或手动内容创建 `session_note` 知识源。
2. 会话结论可一键保存为知识笔记，并立即进入知识库索引。
3. 自动识别并保存 `decisions`、`constraints`、`risks`、`learnings` 四类沉淀 metadata。
4. 同一 session 下相同内容不重复创建知识笔记。
5. 保存后前端给出明确反馈，并能在知识库中检索到保存内容。

## 2. 非目标

1. 不引入 embedding、vector、rerank 或 GraphRAG。
2. 不实现大型“知识沉淀中心”或复杂审核工作流。
3. 不自动保存所有会话消息，避免噪声污染知识库。
4. 不做跨项目知识共享。
5. 不做复杂语义去重；本阶段只做同 session 同内容 hash 去重。
6. 不修改现有 `agent_document` 自动归档策略，只复用其已有入库能力。

## 3. 现有能力复用

现有系统已经具备：

- `fileRepo.createAgentDocument()`：把智能体文档写入 `resource_assets`，并可进入资源库。
- `ingestProjectFileIntoKnowledge()`：把 `uploaded_file` / `agent_document` 解析成 `knowledge_sources`、extraction 和 chunks。
- `knowledge_sources.source_type` 已支持 `session_note`。
- Session 消息和 evidence 已有 session/project 边界。

因此 Phase 3 不新增新表，优先新增一个小服务把 Session 内容直接写成 `session_note` 知识源。

## 4. 数据模型

`session_note` 直接使用现有知识库表：

- `knowledge_sources`
  - `source_type = 'session_note'`
  - `source_id = session_note:<sessionId>:<contentHash>`
  - `project_id = session.project_id`
  - `room_id = null`
  - `title = 用户标题或自动标题`
  - `summary = 自动摘要`
  - `tags_json` 包含 `会话沉淀` 以及识别出的主题标签
  - `metadata_json` 保存 session/message/run 和结构化沉淀字段
- `knowledge_extractions`
  - `plain_text` / `markdown` 保存笔记正文
- `knowledge_chunks`
  - 使用现有 `splitKnowledgeChunks()` 生成 chunks

metadata 示例：

```json
{
  "session_id": "session-1",
  "source_message_id": "message-1",
  "source_role": "assistant",
  "source_agent_id": "planner",
  "content_hash": "abc123",
  "decisions": ["采用 CLI 工具模式"],
  "constraints": ["不读取 SQLite 文件"],
  "risks": ["FTS 中文召回有限"],
  "learnings": ["citation key 必须随回答返回"]
}
```

## 5. 后端 API

新增：

```http
POST /api/sessions/:sessionId/knowledge-notes
```

请求：

```ts
{
  messageId?: string;
  title?: string;
  content?: string;
}
```

规则：

- `messageId` 和 `content` 至少提供一个。
- 提供 `messageId` 时，服务读取该 session 下的消息正文。
- 同时提供 `content` 时，以 `content` 为笔记正文，但仍可把 `messageId` 作为来源。
- 笔记正文 trim 后不能为空。
- `messageId` 必须属于当前 session。
- session 必须属于现有 project。
- 同一 session 下同一正文 hash 返回已有 source，并标记 `deduplicated: true`。

响应：

```ts
{
  source: KnowledgeSource;
  deduplicated: boolean;
  metadata: {
    decisions: string[];
    constraints: string[];
    risks: string[];
    learnings: string[];
  }
}
```

## 6. 知识提取规则

第一版采用 deterministic 文本规则，避免引入 LLM 成本和不可测输出。

识别标题：

- 优先使用请求 `title`。
- 其次使用 Markdown 一级/二级标题。
- 再次使用第一条决策/结论句。
- 最后使用 `会话知识笔记 YYYY-MM-DD`。

识别 metadata：

- `decisions`：匹配 `决策`、`决定`、`结论`、`采用`、`确认`、`选型`。
- `constraints`：匹配 `约束`、`限制`、`不做`、`禁止`、`必须`、`边界`。
- `risks`：匹配 `风险`、`问题`、`阻塞`、`失败`、`注意`。
- `learnings`：匹配 `经验`、`教训`、`复盘`、`正确做法`、`学到`。

输出上限：

- 每类最多 8 条。
- 单条最多 240 字符。
- 总正文沿用知识 ingestion 的 chunk 和 summary 上限。

## 7. 前端入口

在 Session transcript 的 assistant / user 消息上新增一个轻量按钮：

- 文案：`保存为知识`
- 位置：消息 header 的次级操作区。
- 状态：
  - idle：可点击。
  - loading：`保存中`，按钮 disabled。
  - success：toast `已保存为知识笔记`，展示 source title。
  - duplicate：toast `知识笔记已存在`。
  - error：toast 展示 API 错误。

交互原则：

- 不弹 modal，不打断会话。
- 不在消息正文里塞说明文本。
- 成功后 invalidate knowledge 相关 query，保证知识库页面刷新可见。

## 8. 自动沉淀边界

现有 agent 文档自动归档已覆盖高质量长文档输出。本阶段不扩大自动归档条件。

Phase 3 的“自动识别决策、约束、风险和经验”指保存知识笔记时自动识别 metadata，而不是后台自动保存所有消息。

## 9. 验收标准

1. `POST /api/sessions/:sessionId/knowledge-notes` 能把 session message 保存为 `session_note`。
2. 保存后 `knowledge_sources`、`knowledge_extractions`、`knowledge_chunks` 均有记录，并能通过知识搜索命中。
3. 同 session 同内容再次保存不创建重复 source，并返回 `deduplicated: true`。
4. 跨 session message 保存被拒绝。
5. metadata 能识别至少 decisions、constraints、risks、learnings 四类内容。
6. Session UI 消息上可触发保存，并处理 loading/success/duplicate/error 状态。
7. `npm run build` 通过，相关后端和前端测试通过。

## 10. 风险与取舍

- 文本规则可能漏掉隐含决策：接受，后续可引入可配置 LLM 提取。
- hash 去重只能处理完全相同正文：接受，语义去重属于后续扩展。
- 消息保存入口可能增加 UI 密度：使用次级小按钮，保持会话主内容优先。
- `session_note` 不经过 `fileRepo`：这是有意选择，避免把短笔记伪装成文件资源；知识库页面通过 `knowledge_sources` 展示。
