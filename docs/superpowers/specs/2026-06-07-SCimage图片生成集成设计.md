# SCimage 图片生成集成设计

## 背景

用户希望将 `https://github.com/luokai-demo/SCimage` 的 Codex images2 生图软件集成到 OpenDeepSea，并明确要求同时支持三种入口：

1. 独立图片生成工作台。
2. 会话内图片生成工具。
3. 智能体可调用的图片生成能力。

已 clone 并分析 SCimage 仓库，分析版本为 `0bb31f6 发布 1.1.3 并优化滚动交互`。SCimage 当前是一个完整本地图片生成工作台：前端使用 Vue 3、Vite、Pinia，后端使用 Python `ThreadingHTTPServer`，包含 provider 配置、模型发现、任务队列、文生图、图生图、图库、族谱、SSE 事件和本地状态持久化。

OpenDeepSea 当前是 React、Vite、Express、WebSocket、SQLite 的本地优先 ACP 多智能体项目管理系统，已经具备项目文件上传、资源库、会话消息附件和智能体运行上下文。直接嵌入 SCimage 的完整应用会引入双前端、双后端、双状态目录和运行时生命周期冲突，因此本设计采用 OpenDeepSea 原生化集成。

## 目标

- 将图片生成能力变成 OpenDeepSea 的一等项目能力。
- 支持文生图和图生图。
- 支持多套图片 provider 配置：Base URL、API Key、模型、兼容模式、是否支持 `count` 参数。
- 支持任务队列、取消、重试、状态推送和失败诊断。
- 生成结果自动写入项目文件库，并在资源库中可搜索、预览、下载和引用。
- 独立工作台、会话入口、智能体工具共享同一套后端任务和数据模型。
- 第一阶段优先交付稳定可用的核心生成链路，后续再补图库高级分组、图像 lineage 和提示词库。

## 非目标

- 不把 SCimage Vue 前端原样嵌入 OpenDeepSea。
- 不保留 SCimage 的 Python `ThreadingHTTPServer` 作为长期运行主后端。
- 不接入 SCimage 的 pywebview 桌面打包能力。
- 第一期不实现 SCimage 的完整族谱画布、小地图、批量下载和桌面保存桥。
- 不把生成图片登记成 `agent_document`。图片文件应优先进入现有 `files` 表，并作为 `uploaded_file` 类型资源展示。

## 方案选择

### 方案 A：原样托管 SCimage 子应用

将 SCimage 前端构建产物和 Python 服务作为独立子应用挂载到 OpenDeepSea。

优点：

- 最快看到 SCimage 原界面。
- 复用 SCimage 现有功能最多。

缺点：

- 需要同时维护 Vue 与 React 两套 UI。
- Python 服务、端口、状态目录和安全边界需要单独管理。
- 生成结果不能自然进入 OpenDeepSea 项目资源库和会话附件。
- 智能体工具调用需要再做一层代理和结果同步。

结论：不推荐作为长期方向。

### 方案 B：复用 SCimage Python 后端，重画 OpenDeepSea 前端

OpenDeepSea 前端使用 React 重建工作台，Express 后端通过 HTTP 或子进程调用 SCimage Python 服务。

优点：

- 能复用 SCimage 后端的生成链路、provider 兼容策略和队列逻辑。
- 前端体验能融入 OpenDeepSea。

缺点：

- 仍然存在双后端和双状态持久化。
- SSE 事件需要转换为 OpenDeepSea WebSocket 事件。
- Python 服务生命周期、端口冲突、安装依赖和错误恢复会成为长期维护成本。

结论：可作为短期过渡，但不作为最终架构。

### 方案 C：OpenDeepSea 原生图片生成能力

将 SCimage 的核心产品经验和兼容策略移植为 OpenDeepSea 后端模块。前端使用 React 构建原生工作台，会话和智能体工具直接调用同一套 API。

优点：

- 数据、权限、资源库、会话和智能体运行边界统一。
- 图片生成结果可以天然成为项目资源和工作流产物。
- 不引入长期双 runtime。
- 后续可逐步吸收 SCimage 的高级图库、提示词库和 lineage 能力。

缺点：

- 初始实现工作量最大。
- 需要将 SCimage 的 Python 生成链路转写或封装成 OpenDeepSea 可控运行时。

结论：推荐采用。

## 总体架构

新增后端能力域 `image-generation`，作为 OpenDeepSea 的统一图片生成服务。三个产品入口都只调用这个能力域：

- 独立工作台：项目级图片生成页面。
- 会话入口：会话 composer 中的图片生成动作。
- 智能体工具：ACP 运行时可调用的受控 `generate_image` 工具。

图片生成服务负责：

- 管理 provider profile。
- 创建和调度 image job。
- 执行文生图和图生图请求。
- 将生成图片写入项目文件上传目录。
- 在 `files` 表创建文件记录。
- 记录 job、output、source image 和 provider metadata。
- 通过 WebSocket 推送任务状态。

## 后端设计

### 模块边界

建议新增目录：

```text
packages/backend/src/image-generation/
```

核心模块：

- `routes.ts`：图片生成 API。
- `provider-profiles.ts`：provider 配置仓储和校验。
- `provider-models.ts`：模型列表拉取和分类。
- `jobs.ts`：任务仓储、状态流转和查询。
- `queue.ts`：本地任务队列、取消和重试。
- `runtime.ts`：生成执行入口。
- `openai-compatible.ts`：OpenAI 兼容 API 传输层。
- `source-images.ts`：图生图源图解析。
- `outputs.ts`：输出文件写入、`files` 表登记和资源化。
- `events.ts`：WebSocket 事件构造。

### 数据模型

新增 SQLite 表：

```text
image_provider_profiles
image_generation_jobs
image_generation_outputs
image_generation_source_images
```

`image_provider_profiles` 保存：

- `id`
- `name`
- `base_url`
- `api_key`
- `model`
- `compat_profile_id`
- `supports_count_parameter`
- `active`
- `created_at`
- `updated_at`

`image_generation_jobs` 保存：

- `id`
- `project_id`
- `room_id`
- `source_message_id`
- `source_agent_id`
- `source_task_id`
- `provider_profile_id`
- `workflow`
- `prompt`
- `count`
- `quality`
- `size`
- `status`
- `message`
- `error`
- `created_at`
- `started_at`
- `completed_at`
- `updated_at`

`image_generation_outputs` 保存：

- `id`
- `job_id`
- `file_id`
- `slot`
- `name`
- `url`
- `mime_type`
- `size`
- `width`
- `height`
- `created_at`

`image_generation_source_images` 保存：

- `id`
- `job_id`
- `file_id`
- `slot`
- `url`
- `origin_job_id`
- `origin_output_id`
- `created_at`

生成文件仍写入现有项目文件目录：

```text
packages/backend/data/uploads/files/<projectId>/<storedName>
```

每张图片通过 `fileRepo.create` 写入 `files` 表，因此会自然出现在项目资源库里，资源类型为 `uploaded_file`。

### API 设计

项目级 API：

```text
GET    /api/projects/:projectId/image-provider-profiles
POST   /api/projects/:projectId/image-provider-profiles
PATCH  /api/projects/:projectId/image-provider-profiles/:profileId
DELETE /api/projects/:projectId/image-provider-profiles/:profileId
POST   /api/projects/:projectId/image-provider-profiles/models

GET    /api/projects/:projectId/image-jobs
POST   /api/projects/:projectId/image-jobs
GET    /api/projects/:projectId/image-jobs/:jobId
POST   /api/projects/:projectId/image-jobs/:jobId/cancel
POST   /api/projects/:projectId/image-jobs/:jobId/retry
DELETE /api/projects/:projectId/image-jobs/:jobId
```

会话级入口复用 `POST /api/projects/:projectId/image-jobs`，请求体携带 `room_id` 和可选 `source_message_id`。

智能体工具也复用同一创建任务能力，但由后端内部调用服务函数，不通过 HTTP 回环。

### 运行时设计

第一版采用 Node/TypeScript 原生执行 OpenAI-compatible 请求：

- 文生图：优先支持 `/images/generations` 和 OpenAI SDK 等价参数。
- 图生图：支持 `/images/edits`，后续再补 SCimage 的 chat completions 图片兼容路径。
- `supports_count_parameter = true` 时一次请求多图。
- `supports_count_parameter = false` 时拆成多个单图请求，并允许保留部分成功结果。

需要从 SCimage 借鉴但用 TypeScript 实现的策略：

- Base URL 规范化。
- 模型列表拉取失败不阻塞手动模型输入。
- API Key 为空时保留旧密钥。
- 质量、尺寸、数量的归一化。
- 图生图源图数量和大小校验。
- 401、402、403、429、500、502、504 等错误归一化。

### 事件设计

通过现有 `/ws` 推送项目或会话相关事件。建议新增事件类型：

```text
image_job:created
image_job:updated
image_job:output_added
image_job:completed
image_job:failed
image_job:canceled
```

会话页面订阅当前 session 或 room 时，可以收到对应图片任务事件。独立工作台订阅 project 维度事件，保持任务列表和图库刷新。

## 前端设计

### 独立工作台

新增项目级页面，例如：

```text
/projects/:projectId/images
```

页面结构：

- 左侧：生成表单。
- 中部：任务队列和当前任务状态。
- 右侧：项目图片图库。

生成表单包含：

- workflow：文生图、图生图。
- prompt。
- source images：从项目文件库选择图片或上传图片。
- provider profile。
- model。
- size。
- quality。
- count。
- submit、cancel、retry。

图库数据优先来自 `image_generation_outputs` 与 `files` 联合视图，同时允许跳转到资源库详情。

### 会话入口

在 `SessionComposer` 增加图片生成动作：

- 用户点击图片生成按钮，打开紧凑弹窗或侧栏表单。
- 默认使用当前项目和当前会话。
- 可从会话附件、项目资源库或本地上传选择图生图源图。
- 创建任务后在 transcript 中插入一条任务状态消息或活动卡片。
- 任务完成后自动展示生成图片，并将图片作为消息附件或资源引用。

会话内展示不需要完整工作台，只保留当前任务的状态、取消、重试和打开工作台入口。

### 智能体工具

新增受控工具 `generate_image`，输入：

```json
{
  "project_id": "string",
  "room_id": "string | null",
  "task_id": "string | null",
  "prompt": "string",
  "workflow": "generate | image-to-image",
  "source_file_ids": ["string"],
  "count": 1,
  "size": "auto",
  "quality": "auto",
  "provider_profile_id": "string | null"
}
```

输出：

```json
{
  "job_id": "string",
  "status": "completed | failed | canceled",
  "outputs": [
    {
      "file_id": "string",
      "resource_id": "file:<file_id>",
      "url": "string",
      "slot": 1
    }
  ],
  "error": "string | null"
}
```

工具调用必须遵守：

- 只能写入当前项目。
- 源图必须属于当前项目。
- API Key 不回传给模型。
- 生成结果必须登记为项目文件。
- 失败时返回归一化错误，供智能体解释给用户。

## 资源库集成

生成图片以 `uploaded_file` 进入资源库，不新增图片专用资源类型。这样可以复用已有：

- 预览。
- 下载。
- 搜索。
- 消息附件引用。
- 项目文件详情。

为了区分生成来源，在 `files.uploaded_by_id` 和 `uploaded_by_name` 中使用图片生成服务标识，例如：

- `uploaded_by_id = image-generation`
- `uploaded_by_name = 图片生成`

详细生成信息放在 `image_generation_outputs` 和 `image_generation_jobs` 中，而不是塞入 `files` 表。

## 阶段计划

### Phase 1：后端核心能力

- 新增图片 provider profile 表和仓储。
- 新增 image job、output、source image 表和仓储。
- 实现任务创建、队列、取消、重试。
- 实现 OpenAI-compatible 文生图。
- 生成结果写入项目文件目录并登记 `files`。
- 增加定向后端测试。

验收：

- 可以通过 API 创建文生图任务。
- 任务完成后项目资源库出现图片。
- 取消、重试和失败错误归一化可用。

### Phase 2：独立图片工作台

- 新增项目级图片页面。
- 实现 provider 配置表单。
- 实现生成表单、任务列表、结果图库。
- 接入 WebSocket 刷新任务状态。

验收：

- 用户可在项目内完成配置、生成、查看、重试和打开资源详情。

### Phase 3：会话内生成

- 在会话 composer 加图片生成入口。
- 支持当前会话创建任务。
- 任务状态在 transcript 中展示。
- 完成后图片作为会话资源或附件展示。

验收：

- 用户不离开会话即可生成图片。
- 生成图片能被后续消息引用。

### Phase 4：智能体工具

- 注册 `generate_image` 工具。
- 限制项目边界、源图边界和 provider 密钥泄漏。
- 工具结果写入资源库并可被工作流引用。

验收：

- 智能体可以在任务中生成图片。
- 生成结果在资源库和会话中可追踪。

### Phase 5：高级能力

- 图生图。
- 输出 lineage。
- 图库分组。
- 提示词库。
- 批量操作。
- 更完整的多 provider 兼容路径。

## 风险与约束

- OpenAI 图片 API 和第三方兼容 API 的返回格式差异较大，必须隔离在 runtime 适配层。
- API Key 属于敏感配置，不能进入消息、资源内容、日志或智能体上下文。
- 图生图源文件必须校验项目归属，避免跨项目文件读取。
- 图片生成可能耗时较长，任务队列和重启恢复需要明确终止状态。
- 当前工作区已有未提交改动，后续实现必须避免覆盖用户已有修改。
- 第一版如果直接转写全部 SCimage 兼容路径，范围会过大，应先支持主路径再迭代。

- `supports_count_parameter` 为 true 和 false 的数量策略。
- 生成成功后写入 `files` 表。
- 图生图源图项目边界校验。

- 对图片工作台做浏览器 smoke test。

## 决策

采用方案 C：OpenDeepSea 原生图片生成能力。

SCimage 作为产品与兼容策略参考，不作为长期运行的子应用。第一期聚焦后端核心能力和独立工作台，再按会话入口、智能体工具、高级图库能力逐步扩展。
