# 资源页升级知识库设计

- 日期：2026-06-07
- 范围：资源页、项目资源库、文件解析、知识摘要、检索索引、会话/智能体引用
- 当前阶段：设计确认后沉淀，不进入实现

## 1. 背景与现状

当前资源页已经具备“项目文件库”的基础能力：

- 前端 `packages/frontend/src/pages/FilesPage.tsx` 支持项目/房间/类型筛选、搜索、上传、预览、下载与删除入口。
- 后端已有 `files`、`message_file_refs`、`resource_assets` 表，分别承载用户上传文件、消息引用关系和智能体归档文档。
- 资源类型当前主要是 `uploaded_file` 与 `agent_document`。
- `session-file-reference-context.ts` 已能在会话中引用资源库文件，并把部分文本、Markdown 或图片路径注入 runtime 上下文。
- `ACP 系统上下文检索能力设计` 已提出事实查询、FTS、混合检索和可追溯引用方向。

这些能力说明资源页不需要推倒重来。升级方向应该是把“文件列表”扩展为“项目知识库”：原始资源仍可管理，但系统还要理解文件内容、提炼知识、建立索引，并允许用户和智能体在项目、房间、任务和会话中受控使用这些知识。

## 2. 社区方案调研结论

社区成熟方案基本采用同一条链路：

上传或同步资料 → 文档解析 → 清洗与分块 → metadata → 索引 → 检索 → 引用溯源 → 应用或智能体使用。

重点参考：

- Dify Knowledge Base：知识库由 documents 和 chunks 组成，支持 chunk settings、index method、retrieval settings、summary auto-gen 和文档维护。适合作为“资料进入知识库后如何加工和检索”的参考。
  - https://docs.dify.ai/en/guides/knowledge-base
  - https://docs.dify.ai/en/use-dify/knowledge/create-knowledge/chunking-and-cleaning-text
  - https://docs.dify.ai/en/use-dify/knowledge/create-knowledge/setting-indexing-methods
  - https://docs.dify.ai/en/guides/knowledge-base/knowledge-and-documents-maintenance/maintain-knowledge-documents
- Open WebUI Knowledge/RAG：区分 Focused Retrieval 和 Full Context，支持 `#` 引用、citations、异步文件处理、BM25 + vector + rerank、agentic knowledge tools。适合作为“会话中如何使用知识”的参考。
  - https://docs.openwebui.com/features/workspace/knowledge/
  - https://docs.openwebui.com/features/rag
  - https://docs.openwebui.com/troubleshooting/rag/
- RAGFlow DeepDoc：强调 OCR、layout recognition、table structure recognition，适合 PDF、扫描件、复杂表格和图文混排文档。适合作为“复杂文档解析能力”的参考。
  - https://github.com/infiniflow/ragflow/blob/main/deepdoc/README.md
- Unstructured：以 partitioning 处理不同文件格式，并输出结构化 elements。适合作为可插拔文档解析层的参考。
  - https://docs.unstructured.io/open-source/core-functionality/partitioning
- Docling：面向 PDF、Office、图片 OCR、表格结构和 Markdown/JSON 导出。适合作为本地优先解析 sidecar 的候选。
  - https://docling-project.github.io/docling/
  - https://github.com/docling-project/docling

对 OpenDeepSea 的启发：

1. 知识库不是单表字段扩展，而是资源、解析、摘要、chunk、索引、引用的流水线。
2. 第一版应优先实现可追溯的解析和全文检索，避免过早引入向量数据库和知识图谱。
3. 短资料可以 Full Context，长资料必须 Focused Retrieval。
4. 复杂 PDF、图片和表格不能只做纯文本 OCR，应保留布局、页码、表格结构和图片说明。
5. 智能体使用知识时应该调用受控工具或选择明确知识范围，而不是默认把所有知识塞进 prompt。

## 3. 产品定位

将“资源页”升级为“知识库”，面向三个使用场景：

1. 项目资料管理：用户上传图片、文件、文档，系统提取内容、生成摘要和标签，支持检索、预览、重处理和删除。
2. 会话引用增强：用户在会话、任务或房间中显式引用知识，系统按预算注入相关内容，并展示来源。
3. 智能体上下文增强：后续让智能体通过受控工具搜索知识库、读取 chunk、返回引用，而不是依赖静态 prompt。

第一版优先做场景 1，并保留场景 2 的直接入口。场景 3 作为第二阶段自然接入。

## 4. 目标

1. 资源页更名或重构为知识库页面，继续兼容已有上传文件和智能体文档。
2. 支持图片、文本、Markdown、PDF、Office、表格等常见资料进入知识库。
3. 上传后异步解析，形成可查看的提取文本、结构化信息、摘要、标签和处理状态。
4. 支持按项目、房间、类型、处理状态、标签、关键词检索。
5. 支持 SQLite FTS5 级别的全文检索，并为后续 vector/hybrid 检索预留边界。
6. 支持在会话中引用知识资源，保留来源、页码、chunk、图片或表格位置。
7. 删除、禁用、重处理、重新索引语义清晰，不破坏历史消息引用。

## 5. 非目标

1. 第一版不实现完整向量数据库、embedding 管理和复杂 rerank。
2. 第一版不做跨项目全局知识共享，只保留数据模型预留。
3. 第一版不做 GraphRAG、实体关系图谱和自动冲突推理。
4. 第一版不让智能体直接读取任意文件系统路径或数据库表。
5. 第一版不自动把所有资源注入每次会话上下文。
6. 第一版不删除现有 `uploaded_file` / `agent_document` 的兼容语义。

## 6. 核心概念

### 6.1 原始资源

原始资源是用户或智能体产生的可管理对象：

- 用户上传文件：图片、PDF、文本、Office、表格等。
- 智能体文档：已有 `agent_document`。
- 后续可扩展：网页导入、Git 文档同步、会话摘录、手写知识笔记。

原始资源保留文件名、类型、大小、URL、存储路径、来源项目、来源房间、上传者、创建时间、删除状态。

### 6.2 解析产物

解析产物是从原始资源中提取出的机器可用内容：

- `plain_text`：纯文本。
- `markdown`：保留层级和表格的 Markdown。
- `layout_json`：页码、标题、段落、表格、图片、坐标、阅读顺序。
- `table_json`：表格结构化数据。
- `image_captions`：图片说明。
- `ocr_text`：图片或扫描件 OCR 结果。
- `parser_version`：解析器和规则版本。
- `content_hash`：用于判断是否需要重处理。

### 6.3 知识摘要

知识摘要是面向用户和检索的派生产物：

- 文档摘要。
- 章节摘要。
- 自动标签。
- 关键词。
- 关键事实。
- 可选 Q&A pairs。
- 风险、决策、结论类摘录。

摘要必须可重新生成，不能覆盖原文。

### 6.4 知识 Chunk

Chunk 是检索的最小单位，包含：

- 所属资源。
- chunk 文本。
- chunk 类型：正文、标题、表格、图片说明、代码、Q&A、摘要。
- 页码或位置。
- metadata。
- FTS 索引字段。
- 后续可选 embedding 字段或外部向量 ID。

### 6.5 知识集合

第一版默认每个项目一个隐式知识集合。后续可显式支持：

- 项目知识库。
- 房间知识库。
- 任务知识包。
- 用户私有知识草稿。
- 跨项目全局知识。

## 7. 推荐架构

采用四层边界：

1. 资源层：保留并扩展 `files` / `resource_assets`，负责原始资源管理。
2. 解析层：异步 job 读取原始资源，生成 extraction。
3. 知识层：基于 extraction 生成 summary、tags、chunks。
4. 检索与投放层：FTS 搜索、上下文预算、引用溯源、会话/智能体使用。

服务边界建议：

- `knowledgeResourceService`：统一读取原始资源和展示列表。
- `knowledgeIngestionService`：创建解析任务、管理状态、触发重处理。
- `knowledgeExtractionService`：适配文本、图片、PDF、Office、表格解析器。
- `knowledgeSummaryService`：生成摘要、标签、关键事实。
- `knowledgeIndexService`：写入 chunks、FTS 表和后续向量索引。
- `knowledgeRetrievalService`：执行关键词检索、metadata filter、上下文拼装。

这些 service 应复用现有 repo，但避免把解析、检索和页面展示逻辑继续堆进 `fileRepo` 或 `resourceAssetRepo`。

## 9. 解析流水线

### 9.1 触发时机

- 用户上传文件成功后自动创建 `knowledge_source` 和 ingestion job。
- 智能体文档归档为 `agent_document` 后自动创建或更新 `knowledge_source`。
- 用户点击“重新处理”时创建新 job。
- 解析器版本变化时，把受影响 source 标记为 `stale`，由用户或后台批量重处理。

### 9.2 状态机

状态：

- `pending`：等待解析。
- `processing`：正在解析。
- `ready`：解析、摘要和索引完成。
- `failed`：解析失败，保留错误信息和重试入口。
- `disabled`：资源存在但不参与检索。
- `stale`：资源可用，但解析版本或内容已过期。

### 9.3 解析策略

第一版内置策略：

- 纯文本、Markdown、JSON、YAML、CSV：Node.js 直接读取，必要时转 Markdown。
- 图片：保存原图，提取基础 metadata；OCR 和 caption 通过可选 vision-capable LLM 或本地 OCR 适配器。
- PDF：优先提取文本层；扫描件或复杂布局交给 Docling/Unstructured/RAGFlow 类 sidecar。
- DOCX/PPTX/XLSX：优先通过 Docling 或 Unstructured sidecar 转 Markdown/JSON。
- 二进制未知文件：只保留 metadata，不进入全文索引。

### 9.4 失败处理

- 单个文件解析失败不影响上传成功。
- UI 明确显示失败原因、解析器、重试入口。
- 失败资源仍可下载、删除和作为普通附件引用。
- ingestion job 必须有超时和错误截断，不能把完整 stderr 暴露给智能体。

## 10. 摘要与知识提炼

第一版自动生成：

- `source.summary`：100 到 300 字中文摘要。
- `tags`：3 到 8 个标签。
- `key_points`：3 到 8 条要点，存入 metadata。
- `content_kind`：需求、设计、验收、会议、截图、报告、代码说明、其他。

后续扩展：

- Q&A pairs：提升问答召回。
- 决策摘录：识别“决定、结论、约束、风险”。
- 知识冲突候选：同一主题下多个资源结论不一致时提示。
- 过期检测：长期未使用、来源文件更新、关联任务关闭后提示复核。

摘要生成规则：

- 摘要是派生产物，用户可重新生成或手动编辑。
- 摘要不可替代原文；检索结果必须能追溯到原始 chunk。
- 摘要生成失败不阻断全文索引。

## 11. 检索设计

### 11.1 第一版检索

使用 SQLite FTS5 + metadata filter：

```ts
searchKnowledge(input: {
  projectId: string;
  roomId?: string;
  query: string;
  sourceTypes?: string[];
  tags?: string[];
  statuses?: string[];
  limit?: number;
}): KnowledgeSearchResult[]
```

结果包含：

- `source_id`
- `chunk_id`
- `title`
- `snippet`
- `score`
- `source_type`
- `mime_type`
- `page_start`
- `page_end`
- `tags`
- `citation`

### 11.2 上下文模式

参考 Open WebUI，支持两种模式：

- Focused Retrieval：大文档默认模式，只注入 TopK chunks。
- Full Context：短文档或用户显式选择时使用，按预算注入全文或摘要。

第一版规则：

- 小于 20K token 估算的短文档可允许 Full Context。
- 大文档默认 Focused Retrieval。
- 图片默认注入 caption/OCR/metadata；如 runtime 支持 image path，可附带图片路径。
- 表格优先注入 Markdown 表格摘要和相关行列，不把大表完整塞进 prompt。

### 11.3 后续混合检索

第二阶段再引入：

- embedding provider 配置。
- vector index 或外部向量库。
- BM25 + vector hybrid。
- rerank。
- query expansion。
- per-agent retrieval policy。

## 12. 前端体验设计

页面名称建议从“资源库”升级为“知识库”，但保留“资源”作为一级概念。

### 12.1 顶部信息

- 标题：知识库。
- 副标题：当前项目/房间范围、资源数量、已索引数量、失败数量。
- 操作：上传、导入网页、重新处理、设置。

第一版可只实现上传和重新处理。

### 12.2 筛选与搜索

筛选：

- 项目。
- 房间。
- 类型：上传文件、智能体文档、图片、PDF、表格、网页、笔记。
- 状态：已就绪、处理中、失败、已禁用、已过期。
- 标签。

搜索：

- 普通关键词。
- 后续支持 `tag:设计 type:pdf status:ready` 这类高级语法。

### 12.3 列表视图

每项展示：

- 文件或文档标题。
- 来源类型。
- 处理状态。
- 摘要。
- 标签。
- 最近使用位置。
- 大小、创建时间、更新时间。
- 操作：预览、下载、引用、禁用检索、重新处理、删除。

### 12.4 详情抽屉

详情分 Tab：

- 预览：原文件或 Markdown 预览。
- 提取内容：plain text / markdown / OCR。
- 摘要：摘要、要点、标签。
- Chunks：chunk 列表、snippet、页码、启用状态。
- 来源与引用：上传者、房间、消息、任务、被哪些会话/agent run 使用。
- 处理日志：解析器、耗时、错误、版本。

### 12.5 空状态与失败状态

空状态不做营销页，直接提供上传入口和可导入类型。

失败状态要给出可执行动作：

- 重试。
- 作为普通文件保留。
- 下载原文件。
- 删除。

## 13. 会话与智能体集成

### 13.1 显式引用

会话输入框可通过现有 `@` 文件混合搜索或后续 `#` 知识搜索引用知识：

- `@`：偏文件/资源对象。
- `#`：偏知识库/检索范围。

第一版可复用已有 `libraryFileRefs`，但后端应优先使用 `knowledge_source` 和 `knowledge_chunks` 拼装上下文。

### 13.2 Runtime 上下文拼装

上下文块必须包含：

- 资源标题。
- 来源类型。
- 页码或 chunk 位置。
- 是否截断。
- 原始资源 ID。
- citation key。

回答后记录 `knowledge_usage_refs`。

### 13.3 智能体工具

第二阶段给 ACP provider 暴露只读工具：

```ts
knowledge.search
knowledge.read_chunk
knowledge.read_source_summary
knowledge.list_project_sources
```

约束：

- 默认 scope 绑定当前项目。
- 跨项目必须显式允许。
- 工具不暴露原始数据库或任意文件路径。
- 每次调用进入 agent run evidence。

## 14. 权限与安全

1. 上传文件按现有项目边界存储，禁止越权读取其他项目资源。
2. 解析器只读取登记过的 `storage_path`，不接受用户提供的任意路径。
3. 所有 shell/sidecar 调用使用参数数组，不拼接不可信命令。
4. OCR、摘要和索引不能写入密钥或本地绝对路径到可见内容。
5. 大文件设置大小限制、解析超时和内容截断。
6. 删除分为三类：
   - 从检索中禁用：资源保留，不参与搜索。
   - 删除知识记录：保留原始文件，移除 extraction/chunks。
   - 删除原始文件：软删除文件，并禁用相关知识。
7. 历史消息引用不因资源删除而被篡改，只显示“来源已删除”或保留引用快照。

## 15. API 草案

第一版 API：

```ts
GET /projects/:projectId/knowledge/sources
GET /knowledge/sources/:sourceId
POST /projects/:projectId/knowledge/sources/:sourceId/reprocess
PATCH /knowledge/sources/:sourceId
DELETE /knowledge/sources/:sourceId
GET /projects/:projectId/knowledge/search?q=
GET /knowledge/sources/:sourceId/chunks
```

上传仍可沿用：

```ts
POST /projects/:projectId/files
```

上传完成后后端自动创建 knowledge source。后续也可以新增更明确的上传入口：

```ts
POST /projects/:projectId/knowledge/upload
```

## 16. 分期计划

### Phase 1：知识库 MVP

目标：把资源页升级为可解析、可摘要、可检索、可引用的项目知识库。

任务：

1. 新增 `knowledge_sources`、`knowledge_extractions`、`knowledge_chunks`、FTS 表。
2. 上传文件和 `agent_document` 自动映射为 knowledge source。
3. 实现文本/Markdown/CSV/JSON 基础解析。
4. 实现 PDF/Office 解析适配器接口，第一版可先选择 Docling 或 Unstructured sidecar。
5. 实现摘要、标签和要点生成。
6. 实现 FTS 搜索和详情页。
7. 会话引用优先使用 knowledge extraction/chunks。

## 17. 验收标准

Phase 1 验收：

1. 用户上传文本或 Markdown 后，知识库列表显示 `processing` 到 `ready` 状态变化。
2. 已解析资源能查看提取内容、摘要、标签和 chunks。
3. 搜索关键词能命中文档标题、摘要和 chunk 正文。
4. 解析失败资源能显示错误并重试。
5. 现有 `uploaded_file` 与 `agent_document` 仍能在资源/知识库中展示。
6. 会话引用知识资源时，runtime 上下文包含来源标题、chunk 或提取内容、截断标记。
7. 删除或禁用资源后，不再参与新检索；历史引用有可解释状态。
8. `npm run build` 通过。

## 18. 风险与取舍

1. SQLite 大字段风险：第一版可限制解析文本大小；后续将 extraction 大字段迁移到文件存储。
2. 中文 FTS 效果风险：先用 LIKE/FTS5 满足基础搜索，后续评估分词或 embedding。
3. PDF/Office 解析复杂：通过 adapter 封装，避免业务代码绑定单一解析器。
4. 摘要成本风险：摘要异步生成，可失败降级，不阻塞索引。
5. Prompt 膨胀风险：强制使用预算、TopK 和截断标记；短文档才允许 Full Context。
6. 历史兼容风险：保留 `files` / `resource_assets` 语义，用 `knowledge_sources` 做统一映射层。

## 19. 决策

1. 第一版采用“项目资料管理优先，再接 Agent RAG”的路线。
2. 第一版以 SQLite FTS5 和结构化 metadata 为主，不引入向量数据库。
3. 第一版保留现有资源库兼容，不迁移或重命名旧数据主键。
4. 文档解析采用可插拔 adapter；Docling、Unstructured、RAGFlow DeepDoc 作为候选，不在核心业务层硬编码。
5. 会话使用知识必须保留引用来源，不能静默注入不可追溯内容。
