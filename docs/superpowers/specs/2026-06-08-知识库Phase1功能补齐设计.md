# 知识库 Phase 1 功能补齐设计

- 日期：2026-06-08
- 来源设计：`docs/superpowers/specs/2026-06-07-资源页升级知识库设计.md`
- 实施范围：Phase 1 MVP
- 明确后置：Phase 2 Agent RAG、知识沉淀、向量检索和混合检索

## 1. 背景

`/knowledge` 已经从资源页视觉上升级为知识库工作台，并具备三栏 command center 页面结构。后端也已经有 `knowledge_sources`、`knowledge_extractions`、`knowledge_chunks`、`knowledge_chunk_fts` 和 `knowledge_usage_refs` 等基础表，上传文件后会进入 `ingestProjectFileIntoKnowledge`。

当前缺口不是从零设计，而是把已有半成品补成可验收的 Phase 1：

1. 后端只暴露了 `GET /api/knowledge` 列表接口，缺少详情、chunks、搜索、重处理、禁用和删除等操作。
2. `/knowledge` 页面仍显示部分 Stitch 示例数据，例如收藏数、最近使用、存储空间、页数、引用计数和固定分页。
3. 详情面板的 tab 和操作按钮多为静态展示，没有接入真实预览、下载、引用、重处理、禁用和删除。
4. 会话引用仍主要基于 `libraryFileRefs` 和 `fileRepo`，还没有优先使用知识库 extraction/chunks。
5. 移动端仍是横向宽表，不符合原设计中的单列列表和详情抽屉要求。

## 2. Phase 1 目标

Phase 1 的目标是让知识库成为真实可用的项目资料管理、解析、检索和显式引用入口。

必须完成：

1. 上传文本、Markdown、JSON、YAML、CSV 或图片后，知识库能显示真实处理状态。
2. 已解析资源能查看摘要、标签、metadata、提取内容和 chunks。
3. 搜索能命中文档标题、摘要和 chunk 正文。
4. 失败资源能显示错误并支持重处理。
5. 资源能被禁用检索、恢复检索和删除。
6. 预览和下载复用现有资源页能力。
7. 会话显式引用知识资源时，runtime 上下文优先使用知识库 extraction/chunks，并保留来源标题、chunk 或截断标记。
8. 页面删除所有假数据，无法从 API 获得的数据显示为空态或隐藏。
9. 桌面、平板和移动端布局均可用，文本不溢出。

## 3. 非目标

本轮不做以下内容：

1. 不实现 Agent 主动调用 `knowledge.search`、`knowledge.read_chunk` 等工具。
2. 不引入 embedding provider、向量数据库、hybrid search、rerank 或 GraphRAG。
3. 不做跨项目全局知识共享策略。
4. 不做自动会话结论沉淀、知识笔记或过期/冲突检测。
5. 不强依赖 Docling、Unstructured 或 RAGFlow sidecar。PDF 和 Office 在本轮只保证 metadata-only 或 limited 状态可解释。

## 4. 当前系统边界

### 4.1 已有后端能力

- `knowledgeRepo.ensureSource`：按 `project_id + source_type + source_id` upsert source。
- `knowledgeRepo.saveExtraction`：保存解析结果。
- `knowledgeRepo.replaceChunks`：替换 chunks 并写入 FTS。
- `knowledgeRepo.search`：基于 SQLite FTS5 搜索 ready 且 enabled 的 chunks。
- `ingestProjectFileIntoKnowledge`：上传文件或智能体文档进入知识库。
- `extractKnowledgeText`：支持文本类文件、图片 metadata 和未知二进制 metadata-only。

### 4.2 已有前端能力

- `/knowledge` 页面已有三栏布局、顶部统计、搜索、筛选、列表和详情面板。
- `KnowledgeResourceView`、`KnowledgeInspector`、`KnowledgeProjectRail`、`KnowledgeCommandBar` 已存在但当前主页面没有统一复用。
- `FilesPage` 和 `ProjectFilePreviewDialog` 已有预览、下载和删除资源能力，可作为知识库操作复用入口。

## 5. 后端 API 设计

所有接口使用 `/api` 前缀。

### 5.1 列表

继续保留：

```http
GET /api/knowledge
```

Query：

- `projectId`
- `roomId`
- `status`
- `sourceType`
- `q`
- `limit`
- `offset`

返回 source list item，并补充：

- `chunk_count`
- `latest_extraction_id`
- `latest_extraction_at`
- `project_name`
- `room_name`
- `reference_count`

`q` 用于 source 级快速过滤，匹配 title、summary、tags、source_id 和 description。全文 chunk 检索使用独立 search API。

### 5.2 详情

新增：

```http
GET /api/knowledge/sources/:sourceId
```

返回：

- source 基础字段
- 最新 extraction 摘要
- 处理 metadata
- 关联原始文件或 agent document 的 preview/download 能力
- 可见引用统计

如果 source 不存在返回 404。如果 source 所属项目不可见，返回 404，避免暴露跨项目存在性。

### 5.3 提取内容

新增：

```http
GET /api/knowledge/sources/:sourceId/extraction
```

返回最新 extraction：

- `plain_text`
- `markdown`
- `metadata`
- `created_at`

大文本按上限返回，并带：

- `truncated`
- `returned_char_count`
- `original_char_count`

### 5.4 Chunks

新增：

```http
GET /api/knowledge/sources/:sourceId/chunks
```

Query：

- `enabled`
- `limit`
- `offset`

返回 chunk 列表，包含 `chunk_index`、`chunk_type`、`heading`、`content`、`token_estimate`、`enabled` 和 metadata 中的 `page_start/page_end/content_hash`。

### 5.5 全文搜索

新增：

```http
GET /api/knowledge/search
```

Query：

- `projectId`，必填
- `roomId`
- `q`，必填
- `status`
- `sourceType`
- `limit`

返回 `KnowledgeSearchResult[]`，使用现有 `knowledgeRepo.search`。搜索结果必须带 citation：

- source title
- source id
- chunk id
- chunk index
- room id
- snippet

### 5.6 重处理

新增：

```http
POST /api/knowledge/sources/:sourceId/reprocess
```

行为：

1. 找到 source 对应的原始 `files` 或 `resource_assets`。
2. 调用 `ingestProjectFileIntoKnowledge`。
3. 返回更新后的 source。

如果原始文件已删除或不可读，source 标记为 `failed`，保留错误和原始 metadata。

### 5.7 状态更新

新增：

```http
PATCH /api/knowledge/sources/:sourceId
```

允许字段：

- `status`: `ready | disabled | stale`
- `enabled`: 用于批量打开或关闭该 source 的 chunks 检索
- `tags`
- `summary`

禁用检索时，source 状态设为 `disabled`，chunks 保留但不参与新搜索，并在 metadata 中记录 `previous_status`。恢复检索时先读取 `previous_status`；如果缺失，则有 enabled chunks 的 source 恢复为 `ready`，没有 chunks 的 source 恢复为 `stale`，提示用户重新处理。

### 5.8 删除

新增：

```http
DELETE /api/knowledge/sources/:sourceId
```

删除语义：

1. 默认删除知识记录：删除 `knowledge_sources` 及其 extraction/chunks/FTS，保留原始文件。
2. 如果 query 带 `deleteOriginal=1`，对 `uploaded_file` 调用现有文件删除逻辑，对 `agent_document` 调用现有 resource asset 删除逻辑。
3. 历史消息引用不回写、不篡改，只在后续详情展示时显示来源已删除或无法访问。

## 6. 后端服务设计

新增轻量服务层，避免 route 直接堆逻辑：

- `knowledgeSourceService`：source 详情、原始资源映射、权限校验。
- `knowledgeActionService`：重处理、禁用、恢复、删除。
- `knowledgeSearchService`：封装 FTS 查询、filter 和 citation 输出。
- `knowledgeReferenceService`：为会话显式引用提供上下文拼装。

第一版 service 可以复用现有 repo，不强行大规模重构。`knowledgeRepo` 继续承担数据库读写，service 负责业务语义和跨 repo 协调。

## 7. 前端页面设计

### 7.1 页面数据原则

`/knowledge` 禁止再显示设计稿假数据。所有数字遵循：

1. API 有值则展示。
2. API 无值但语义必要则显示 `0`、`暂无` 或 `未记录`。
3. API 无法证明的概念先隐藏，例如收藏、回收站、固定存储空间和固定页数。

### 7.2 页面结构

保留当前三栏结构：

- 左侧 rail：范围、类型、状态和项目筛选。
- 中央主区：统计、搜索、筛选、列表/网格、分页。
- 右侧 inspector：概览、预览、解析、摘要、chunks、引用和处理日志。

当前 `KnowledgePage.tsx` 文件偏大，实施时应把表格、详情、统计和操作栏拆回组件，优先复用已存在的：

- `KnowledgeResourceView`
- `KnowledgeInspector`
- `KnowledgeProjectRail`
- `KnowledgeCommandBar`

如果复用成本高，可以先保留页面结构，但要消除重复类型和重复展示逻辑。

### 7.3 列表与搜索

列表模式用于大量资源比较，网格模式用于图片和文档预览。搜索分两层：

- 快速筛选：当前已加载列表内过滤，适合 title、tag、status。
- 全文检索：调用 `/api/knowledge/search`，展示 chunk snippet 和 citation。

用户输入关键词后：

1. 如果没有选中项目，先做 source 级全局列表过滤。
2. 如果选中项目，优先调用全文搜索。
3. 搜索结果中按 source 聚合显示命中 chunk 数，详情面板展示具体 chunks。

### 7.4 详情面板

详情 tab：

1. 概览：状态、摘要、标签、关键 metadata。
2. 预览：复用 `ProjectFilePreviewDialog` 或内联预览能力。
3. 解析：显示 extraction 的 plain text / markdown，支持截断提示。
4. 摘要：显示 summary、key_points、content_kind、tags。
5. Chunks：显示 chunk 列表、snippet、token、enabled。
6. 引用/日志：显示引用计数、最近使用位置、parser、parser_version、last_processed_at、error。

如果没有选中资源，右侧显示当前筛选范围概览，而不是展示第一条资源的假详情。

### 7.5 操作

操作按钮必须有真实行为：

- `预览资源`：打开预览 dialog。
- `下载文件`：仅原始文件可下载时显示。
- `引用到会话`：打开选择会话或提示从会话页使用该资源，第一版至少复制/生成可引用资源 ID。
- `重新处理`：调用 reprocess API，成功后刷新 source、chunks 和统计。
- `禁用检索` / `恢复检索`：调用 PATCH。
- `删除资源`：危险区，二次确认，默认只删除知识记录。

`批量操作` 第一版只在有选中资源时出现。未实现批量行为前不显示。

### 7.6 响应式

- `>= 1280px`：完整三栏。
- `1024px - 1279px`：右侧 inspector 可收起。
- `768px - 1023px`：左 rail 压缩，主区 2 列或紧凑列表。
- `< 768px`：隐藏左 rail，主区单列列表，筛选进入抽屉，详情进入全屏抽屉，宽表不横向撑破首屏。

移动端不保留固定宽表作为主体验。

## 8. 会话引用设计

Phase 1 不实现 `#` 知识搜索和 Agent RAG 工具，只补显式引用。

行为：

1. 用户从知识库选择资源并引用到会话。
2. 会话消息 metadata 继续保留 `library_file_refs` 兼容字段。
3. 后端构建 runtime 上下文时，优先查找对应 `knowledge_source`。
4. 如果 source ready 且有 chunks，按预算注入 chunks 或 extraction。
5. 如果 source 没有 chunks，降级为现有文件 metadata 或文本读取逻辑。

上下文块必须包含：

- 资源标题
- source id
- chunk id 或 extraction id
- 是否截断
- source type
- citation key

本轮记录 `knowledge_usage_refs`，ref_type 使用：

- `manual_reference`
- `session_message`

## 9. 错误处理

### 9.1 解析失败

解析失败不影响上传成功。source 状态为 `failed`，保留：

- 错误摘要
- parser
- parser_version
- last_processed_at
- 原始文件 metadata

UI 提供：

- 重处理
- 下载原文件
- 删除知识记录

### 9.2 不支持格式

PDF、Office 和未知二进制在本轮允许 metadata-only。UI 展示为 `待解析能力扩展` 或 `仅 metadata`，不能伪装为已提取全文。

### 9.3 删除与历史引用

删除知识记录不删除历史消息。历史引用展示时，如果 source 不存在，显示 `来源已删除`。如果原始文件也删除，下载和预览入口隐藏。

## 10. 测试设计

### 10.1 后端测试

新增或扩展 route tests：

1. `GET /api/knowledge/sources/:sourceId` 返回详情、project/room label、latest extraction。
2. `GET /api/knowledge/sources/:sourceId/chunks` 返回 chunks 并支持 enabled filter。
3. `GET /api/knowledge/search` 命中 chunk 正文并返回 citation。
4. `POST /api/knowledge/sources/:sourceId/reprocess` 成功刷新 failed source。
5. `PATCH /api/knowledge/sources/:sourceId` 可禁用和恢复检索。
6. `DELETE /api/knowledge/sources/:sourceId` 默认删除知识记录但保留原始文件。
7. 跨项目 source 访问返回 404 或权限等价结果。

### 10.2 前端测试

新增或扩展组件测试：

1. `/knowledge` 统计卡不使用 fallback 假数据。
2. 只有真实资源时列表显示真实标题、状态、大小和 chunk 数。
3. 搜索输入会触发正确 API 或本地筛选路径。
4. 详情 tab 显示 extraction、summary 和 chunks。
5. 预览、下载、重处理、禁用、删除按钮按能力显示或禁用。
6. 无选中资源时 inspector 显示范围概览。
7. 移动端关键文本不溢出，宽表不是主视图。

### 10.3 验证命令

至少运行：

```bash
npm run build
```

如实施过程中新增 test script，补充运行对应命令。前端可见变化需用 Playwright 截取桌面和移动端截图。

## 11. 验收标准

Phase 1 完成时必须满足：

1. 用户上传文本或 Markdown 后，知识库列表显示 ready，详情能看到 extraction、summary 和 chunks。
2. 用户上传图片后，知识库显示 ready 或 metadata-only，详情不伪造 chunk 和页数。
3. 搜索关键词能命中标题、摘要和 chunk 正文。
4. 失败资源显示错误，并能通过重处理恢复。
5. 禁用资源后不再参与全文检索，恢复后重新参与。
6. 删除知识记录后列表和搜索不再出现该 source，原始文件默认保留。
7. 预览和下载对可用原始文件生效。
8. 会话引用知识资源时 runtime 上下文包含可追溯来源和截断标记。
9. `/knowledge` 不再出现无法从真实数据证明的固定计数。
10. 桌面和移动端截图验证页面可用，无明显文本重叠或主内容横向撑破。
11. `npm run build` 通过。

## 12. 实施顺序建议

1. 后端 API 和 route tests。
2. 前端 API client 和类型。
3. `/knowledge` 去假数据，统一真实 source/list/stat。
4. 详情 tab 接 extraction/chunks/search。
5. 操作接入 preview/download/reprocess/disable/delete。
6. 会话引用上下文优先 knowledge source。
7. 响应式和视觉收尾。
8. 最终 build、测试、Playwright 截图和代码审查。

## 13. 决策

1. 本轮只做 Phase 1 MVP，不做 Phase 2 Agent RAG。
2. 第一版全文检索使用现有 SQLite FTS5，不引入向量检索。
3. PDF/Office 不阻塞 Phase 1，必须以真实 limited 状态展示，不伪造提取结果。
4. 原始文件和知识记录分离删除，默认删除知识记录，保留原始文件。
5. 页面所有统计和详情必须来自真实数据或明确空态，不保留 Stitch 示例数字。
