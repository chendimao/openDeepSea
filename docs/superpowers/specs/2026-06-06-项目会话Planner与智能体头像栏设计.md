# 项目会话 Planner 与智能体头像栏设计

## 背景

当前 Session Workspace 中普通消息发送路径仍由前端传入 `agentId: 'planner'`，但实际 ACP 后端来自 `sessions.provider`。这导致页面看起来运行的是 `planner`，实际运行配置却绕过了系统内置 `planner` 智能体的默认 ACP 后端、权限模式、工具策略、工作区策略和记忆作用域。

同时，Session 页全局 header 右侧仍显示单个 Profile 头像。用户希望把这个位置下沉到项目菜单栏右侧，显示当前项目实际使用到的多个智能体，并通过头像进入对应智能体设置。

## 目标

1. Session Workspace 默认使用系统内置 `planner` 智能体作为会话运行智能体。
2. 项目设置可以控制 Session Planner 的 ACP 后端：继承系统默认或项目覆盖为 Codex、Claude Code、OpenCode。
3. Session Planner 运行时使用内置 `planner` 的完整 runtime profile，而不只使用后端字段。
4. 项目设置变更立即影响当前项目所有 active Session 的后续 run。
5. 正在运行的 run 不被打断、不自动重放，历史 run 继续保留当时使用的 provider。
6. Session 页项目菜单栏右侧显示当前项目用到的智能体头像组。
7. 点击智能体头像可以进入对应智能体设置入口。

## 非目标

1. 不在本次设计中重构 Room Agent dispatcher。
2. 不把 Session Workspace 绑定到隐藏 Room 或隐藏 Room Agent。
3. 不在项目级 Session Planner 设置中编辑系统内置 `planner` 的完整 agent profile；初版只允许切换项目级 ACP 后端覆盖。
4. 不让项目设置变更中断正在运行的 ACP 调用。
5. 不把全局智能体库中未被项目使用的智能体显示在项目头像栏。

## 术语

- **系统内置 planner**：全局 agents 表中 `builtin_key = 'planner'` 或 `agent_id = 'planner'` 的内置智能体。
- **Session Planner**：Session Workspace 中用于响应普通会话消息的默认智能体。它固定映射到系统内置 planner。
- **项目覆盖 backend**：项目 settings 中针对 Session Planner 选择的 ACP 后端覆盖值。
- **项目用到的智能体**：项目下所有 Room 中出现过的 active room agents，加上 Session 内置 planner。

## 数据模型

在现有 settings 作用域上扩展项目级字段：

```ts
session_planner_acp_backend: AcpBackend | null
```

含义：

- `null`：继承系统内置 planner 的默认 ACP 后端。
- `'codex' | 'claudecode' | 'opencode'`：项目级覆盖。

数据库可在 `settings` 表中新增 nullable 列：

```sql
session_planner_acp_backend TEXT NULL
```

系统层不需要新增同名默认值，因为系统默认值已经由内置 `planner.default_acp_backend` 表达。项目 settings 的 GET/PATCH 需要包含该字段，并在 settings resolution 中给出 effective 值，便于前端展示“当前继承：Codex”。

为保证历史 run 可追溯，`session_runs` 建议新增运行边界快照字段：

```sql
runtime_profile_snapshot TEXT NULL
```

内容为 JSON，记录 run 创建时解析出的 permission mode、runtime backend、tool policy、workspace policy、memory scope 和 backend source。`provider` 字段仍继续记录本轮实际 ACP 后端。

## 后端运行解析

新增 resolver：

```ts
resolveSessionPlannerRuntime(projectId: string): SessionPlannerRuntime
```

返回结构：

```ts
type SessionPlannerRuntime = {
  agent: Agent;
  agentId: 'planner';
  backend: AcpBackend;
  backendSource: 'project' | 'builtin';
  projectOverrideBackend: AcpBackend | null;
  permissionMode: AcpPermissionMode;
  runtimeBackend: AgentRuntimeBackend;
  toolPolicy: AgentToolPolicy;
  workspacePolicy: AgentWorkspacePolicy;
  memoryScope: AgentMemoryScope;
};
```

解析规则：

1. 找到系统内置 planner。优先 `agentRepo.getByBuiltinKey('planner')`，兜底 `agentRepo.getByAgentId('planner')`。
2. 读取项目 settings 的 `session_planner_acp_backend`。
3. 如果项目覆盖值存在，则使用覆盖值作为 backend。
4. 如果项目覆盖值为空，则使用内置 planner 的 `default_acp_backend`。
5. runtime profile 始终来自内置 planner 的默认配置：
   - `default_acp_permission_mode`
   - `default_runtime_backend`
   - `default_tool_policy`
   - `default_workspace_policy`
   - `default_memory_scope`
6. 如果内置 planner 不存在或没有可用 backend，后端返回明确错误，不静默回退到硬编码 `codex`。

## Session 消息流程

普通消息发送流程调整为：

```text
Session 页面输入
→ session.message.send
→ 后端读取 session.project_id
→ resolveSessionPlannerRuntime(project_id)
→ 创建 SessionMessage，metadata.target_agent_id = planner
→ buildRuntimePrompt(session, userMessage.content)
→ runSessionAgent(resolvedSessionPlannerRuntime)
→ ACP adapter
→ WebSocket 推送 run/message/evidence
```

前端可以继续传 `agentId: 'planner'` 作为目标语义，但后端不再相信前端传入的 backend 语义。Session Runtime 的 provider、permission、工具和 workspace 权限都由后端 resolver 决定。

`/new` 创建的新 Session 不再从旧 session 的 `provider` 复制运行配置。新 Session 的后续 run 会重新通过项目设置解析 backend。历史字段 `sessions.provider` 可保留兼容，但不再作为 Session Planner 的权威配置来源。

## 运行中切换语义

项目设置变更立即影响当前项目下所有 active Session 的后续 run，但不影响已经创建的 run。

行为规则：

1. 正在运行的 run 不停止。
2. 正在运行的 run 不自动重试。
3. run 记录保留创建时解析出来的 provider、model、permission/profile 快照。
4. 下一次用户发送消息时，重新解析最新项目设置。
5. 如果切换 backend，ACP session 复用按 `session_id + agent_id + provider` 维度隔离；不同 provider 不复用同一个 provider session id。

## 项目设置 UI

在 `ProjectSettingsDialog` 中新增“会话规划智能体”小节。

展示内容：

- 固定智能体：系统内置 Planner。
- ACP 后端：继承系统默认 / Codex / Claude Code / OpenCode。
- 继承状态：选择继承时显示当前继承结果，例如“当前继承：Codex”。
- 影响说明：更改会立即影响本项目 active Session 的后续运行，不会中断正在运行的任务。
- 运行边界说明：显示 planner 当前 permission mode、tool policy、workspace policy、memory scope，初版只读。

不复用 `AcpConfigPanel` 作为项目级设置主体，因为 `AcpConfigPanel` 面向 room-agent binding，包含 `acp_session_id`、workflow role、移除 agent、转移任务等 Room 语义。项目级 Session Planner 设置只管理项目覆盖 backend。

## 项目智能体头像栏

Session 页顶部项目菜单栏右侧新增 `ProjectAgentStrip`。

位置：

- 位于 Session 页项目菜单栏右侧。
- 靠近 Compact、Fork、Context Pressure、Settings。
- Session Workspace 中隐藏或移除全局 header 最右侧单个 Profile 头像。

数据来源：

1. 项目下所有 Room 中出现过的 active room agents。
2. 加上 Session 内置 planner。
3. 去重优先级：
   - 有 `global_agent_id` 时按 `global_agent_id` 去重。
   - 没有 `global_agent_id` 时按 `agent_id` 去重。
4. `planner` 永远显示，即使项目下没有 Room。

展示规则：

- 默认显示 4 到 5 个头像。
- 超出数量显示 `+N` 折叠入口。
- 头像显示智能体名称首字或已有头像组件样式。
- 有可用 ACP backend 时显示 active 状态点。
- hover tooltip 展示智能体名称、backend、来源房间数量。

## 头像点击行为

点击 `planner` 头像：

- 打开项目级 Session Planner 设置。
- 可切换继承 / Codex / Claude Code / OpenCode。
- 显示 planner runtime profile 的只读摘要。
- 如需编辑内置 planner 完整 profile，提供跳转到全局“智能体”页面的入口。

点击其他智能体头像：

- 如果该智能体在项目中只有一个 active room-agent binding，直接打开该 binding 的 ACP/runtime 设置面板。
- 如果该智能体在多个 room 中出现，先打开 binding 选择 popover。
- binding 选择项显示：
  - Room 名称
  - 智能体名称
  - 当前 backend
  - workflow role
- 用户选择 binding 后打开现有 `AcpConfigPanel` 风格的设置面板。

这样可以避免把 room-agent 的 `acp_session_id`、workflow role、移除/转移等语义误放到项目级全局 agent 上。

## API 设计

新增项目智能体聚合接口：

```http
GET /api/projects/:projectId/agents/used
```

返回：

```ts
type ProjectUsedAgentsPayload = {
  planner: {
    kind: 'session_planner';
    agent_id: 'planner';
    name: string;
    effective_acp_backend: AcpBackend;
    project_override_acp_backend: AcpBackend | null;
    backend_source: 'project' | 'builtin';
    runtime_profile: {
      permission_mode: AcpPermissionMode;
      runtime_backend: AgentRuntimeBackend;
      tool_policy: AgentToolPolicy;
      workspace_policy: AgentWorkspacePolicy;
      memory_scope: AgentMemoryScope;
    };
  };
  agents: Array<{
    kind: 'room_agent';
    global_agent_id: string | null;
    agent_id: string;
    name: string;
    acp_enabled: boolean;
    acp_backend: AcpBackend | null;
    room_bindings: Array<{
      room_id: string;
      room_name: string;
      room_agent_id: string;
      acp_backend: AcpBackend | null;
      workflow_role: WorkflowRole | null;
    }>;
  }>;
};
```

前端使用 React Query 单独加载该接口，不把头像数据塞进每个 Session WebSocket snapshot。原因是头像组变化频率低，独立接口更容易缓存、刷新和测试。

## 错误处理

1. 项目不存在：返回 404。
2. 内置 planner 缺失：返回 500 或 session error，提示“系统内置 Planner 不可用”。
3. 项目覆盖 backend 非法：PATCH settings 返回 400。
4. 选择 room-agent binding 时 binding 已被移除：提示刷新，并重新拉取项目 used agents。
5. backend 切换后 provider adapter 不可用：run 失败并记录 blocker/evidence，不影响 settings 保存。

## 测试计划

后端测试：

1. `settingsRepo` 保存和解析 `session_planner_acp_backend`。
2. `resolveSessionPlannerRuntime` 在项目覆盖存在时使用项目 backend。
3. `resolveSessionPlannerRuntime` 在项目覆盖为空时继承内置 planner backend。
4. resolver 返回内置 planner 的完整 runtime profile。
5. Session message dispatch 使用 resolver 的 backend，而不是 `sessions.provider`。
6. backend 切换后新 run 使用新 provider，旧 run provider 不变。
7. `GET /api/projects/:projectId/agents/used` 返回 planner 和项目 room agents，并正确去重。

前端测试：

1. Project settings 表单渲染 Session Planner 小节。
2. 选择继承或具体 backend 时 PATCH 正确 payload。
3. Session 项目菜单栏显示项目智能体头像组。
4. `planner` 头像点击打开项目 Session Planner 设置。
5. 多 room binding 的智能体点击后显示 binding 选择。
6. Session Workspace 中不再显示全局 header profile 头像。

## 验收标准

1. Session 页面后续 run 使用系统内置 `planner` 的 runtime profile。
2. 项目设置可以选择 Session Planner backend 的继承或覆盖。
3. 修改项目设置后，不中断当前 run；下一次消息使用新 backend。
4. run 记录中 provider 可追溯，旧 run 不被改写。
5. Session 页全局 header 不再显示单个 Profile 头像。
6. Session 项目菜单栏右侧显示项目用到的智能体头像组。
7. 头像组至少包含内置 planner。
8. 点击 planner 头像可以进入项目 Session Planner 设置。
9. 点击其他智能体头像可以进入对应 room-agent 设置选择流程。
10. 超出展示数量的智能体通过 `+N` 折叠入口访问。

## 迁移与兼容

1. 旧 `sessions.provider` 字段保留，用于历史显示和兼容旧数据。
2. 新 run 的 provider 来源改为 resolver。
3. 旧项目 settings 没有 `session_planner_acp_backend` 时默认继承系统内置 planner。
4. 已存在的 active Session 不需要迁移；下一次发送消息自然使用新解析逻辑。
5. 内置 planner 的系统默认 backend 仍由全局智能体库维护，项目覆盖不会修改全局 planner。
