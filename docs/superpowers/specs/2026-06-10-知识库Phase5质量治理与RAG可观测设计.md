## 1. 背景

当前知识库已经完成从资源列表到最小知识库的升级。已有能力包括：

1. `knowledge_sources`、`knowledge_extractions`、`knowledge_chunks`、FTS 和 embedding 存储。
2. keyword、vector_preview、hybrid 三种检索模式。
3. manual、URL、workspace docs、uploaded file、agent document、session note 等来源。
4. Agent RAG CLI、citation、usage refs 和 task/workflow/collaboration agent 注入。
5. duplicates、stale、parser_incomplete、empty_index 等治理信号。
6. local-hash 和 openai-compatible embedding provider、测试 provider、重建索引和索引覆盖状态。
7. `/knowledge` 三栏工作台，包含筛选、搜索、导入、治理提示、详情、chunks、引用和 metadata 编辑。

这些能力已经不是空壳 MVP，但仍属于最小闭环：用户能导入和检索，Agent 能调用工具，页面能显示基础治理信号。下一阶段的问题不再是“有没有知识库”，而是“知识库是否可信、检索是否有效、Agent 使用是否可追溯、治理问题是否能被处理”。

## 2. 当前缺口

### 2.1 检索质量不可度量

hybrid 检索已经有 ranking metadata，但缺少评测集、query 日志、结果反馈和命中解释。用户只能看到结果，无法判断排序好坏，也无法持续改进检索质量。

### 2.2 RAG 使用不可回放

`knowledge_usage_refs` 已记录 usage，但页面没有形成“某次 Agent 回答用了哪些 query、命中了哪些 chunk、引用是否真实被使用、是否发生 fallback”的可观测视图。

### 2.3 治理信号不可操作

当前治理提示能指出 duplicate、stale、parser incomplete、empty index，但缺少处理动作。例如合并重复、重新处理过期来源、忽略已知问题、批量重建索引、禁用空索引来源。

### 2.4 知识沉淀缺少候选队列

会话消息可以手动保存为知识，metadata 也可编辑，但从任务验收、代码审查、计划文档、Agent run 输出中自动发现候选知识的链路尚未形成。长期使用后，知识库会依赖用户手动整理。

### 2.5 页面信息架构需要分层

当前 `/knowledge` 页面承载搜索、资源管理、导入、embedding 运维、治理提示和详情编辑。最小闭环可用，但随着质量治理和 RAG 观测加入，需要明确视图层次，避免继续把所有操作塞入同一工具条。

## 3. 目标

Phase 5 目标是把知识库从“可用”推进到“可信、可治理、可观测”：

1. 建立检索质量闭环：记录 query、结果、ranking、用户反馈和命中解释。
2. 建立 RAG 使用观测：能回放 Agent 使用知识的查询、结果、citation、fallback 和引用链。
3. 建立治理工作流：治理信号能转化为可执行动作，并记录处理状态。
4. 建立知识沉淀候选流：从会话、任务、workflow artifact 和 Agent run 中生成候选知识，用户确认后入库。
5. 优化 `/knowledge` 信息架构：保持三栏工作台，但增加明确的视图模式和任务化操作区。
6. 为后续复杂解析 sidecar、知识集合和跨项目共享保留扩展边界。

## 4. 非目标

1. 不在 Phase 5 接入外部 vector database。
2. 不实现 GraphRAG、实体关系图谱或自动事实冲突推理。
3. 不强制安装 Docling、Unstructured、OCR 或 Python sidecar。
4. 不默认抓取任意 URL 内容。
5. 不自动把所有知识预检索并塞进 Agent prompt。
6. 不做跨项目全局知识共享的完整权限系统。
7. 不把知识库页面重做成营销式或低密度内容管理后台。

## 5. 方案选择

### 方案 A：质量治理与 RAG 可观测优先

先补检索日志、RAG usage 回放、治理动作和候选知识队列。保留现有 parser 和 embedding 架构。

优点：

- 直接提升当前知识库可信度。
- 能用现有数据模型渐进增强。
- 为后续复杂解析和集合管理提供真实使用数据。

缺点：

- 复杂 PDF、OCR 和 Office 解析仍然只是可解释状态，不会在本阶段大幅改善。

### 方案 B：复杂解析 sidecar 优先

先接 parser provider registry 和可选 sidecar，让 PDF、Office、图片 OCR 产生更高质量 chunks。

优点：

- 对资料型项目收益明显。
- 能改善 parser_incomplete 的根因。

缺点：

- 环境和依赖复杂度高。
- 如果没有检索质量观测，解析质量提升不容易量化。

### 方案 C：页面重构优先

先重构 `/knowledge` 的信息架构和视觉层级，把资源、治理、RAG 观测和设置拆成更清晰的视图。

优点：

- 用户体验改善快。
- 有利于后续能力承载。

缺点：

- 如果后端质量数据不完整，页面重构只能改善操作感，无法提升知识可靠性。

本阶段采用方案 A。页面只做支撑质量治理和 RAG 观测的结构增强，不做大规模视觉重绘。

## 6. 总体架构

Phase 5 在现有知识库边界上增加四个服务层：

1. `knowledgeQueryLogService`：记录用户和 Agent 发起的知识检索请求、检索模式、provider、结果摘要和错误。
2. `knowledgeEvaluationService`：维护评测 query、人工反馈、结果相关性和检索质量指标。
3. `knowledgeGovernanceActionService`：把治理信号转成可操作项，支持处理、忽略、批量重建和重新处理。
4. `knowledgeCandidateService`：从会话消息、Agent run、workflow artifact 和任务验收输出中生成候选知识，并在用户确认后写入现有 import/note 服务。

现有服务继续保留：

- `knowledgeRepo` 负责持久化 sources、extractions、chunks、embeddings 和 usage refs。
- `knowledgeSearchService` 负责搜索和 ranking。
- `knowledgeRagService` 负责 Agent 工具响应、citation 和 usage refs。
- `knowledgeEmbeddingProvider` 和 `knowledgeEmbeddingRebuild` 负责 provider、测试和重建。

## 7. 数据模型建议

### 7.1 `knowledge_query_logs`

记录每次搜索行为，服务质量分析和 RAG 回放。

字段：

- `id`
- `project_id`
- `room_id`
- `actor_type`：`user`、`agent`、`session_agent`、`system`
- `actor_id`
- `query`
- `mode`
- `provider`
- `model`
- `result_count`
- `top_result_source_id`
- `top_result_chunk_id`
- `fallback`
- `error`
- `metadata_json`
- `created_at`

用户页面搜索和 `openclaw:knowledge search` 都应写入日志。只记录 query 和结果 metadata，不保存完整 chunk 原文。

### 7.2 `knowledge_query_results`

记录一次 query 返回的前若干结果，用于回放和反馈。

字段：

- `id`
- `query_log_id`
- `rank`
- `source_id`
- `chunk_id`
- `score`
- `retrieval_mode`
- `ranking_json`
- `citation_key`
- `snippet`
- `created_at`

`snippet` 限制长度，只用于回放，不替代原 chunk。

### 7.3 `knowledge_feedback`

记录人工反馈和后续自动评价。

字段：

- `id`
- `query_log_id`
- `result_id`
- `source_id`
- `chunk_id`
- `feedback`：`relevant`、`irrelevant`、`useful`、`wrong_scope`、`stale`、`missing_context`
- `note`
- `created_by`
- `created_at`

### 7.4 `knowledge_governance_actions`

把治理信号转成可处理事项。

字段：

- `id`
- `project_id`
- `room_id`
- `source_id`
- `action_type`：`merge_duplicate`、`reprocess_stale`、`rebuild_empty_index`、`disable_empty_source`、`ignore_parser_incomplete`、`review_metadata`
- `status`：`open`、`processing`、`completed`、`ignored`、`failed`
- `reason`
- `metadata_json`
- `created_at`
- `updated_at`
- `resolved_at`

同一个 source 和 action_type 在 open 状态下只保留一条，避免治理列表重复膨胀。

### 7.5 `knowledge_candidates`

记录待确认的知识沉淀候选。

字段：

- `id`
- `project_id`
- `room_id`
- `source_ref_type`：`session_message`、`agent_run`、`workflow_artifact`、`task_event`
- `source_ref_id`
- `title`
- `content`
- `summary`
- `tags_json`
- `metadata_json`
- `confidence`
- `status`：`pending`、`accepted`、`rejected`、`merged`
- `created_at`
- `updated_at`

候选被接受后，复用 manual 或 session_note 写入现有 `knowledge_sources`，并记录候选到 source 的关系。

## 8. 后端能力设计

### 8.1 Query log 写入

所有知识搜索入口统一写 query log：

- `GET /api/knowledge/search`
- `openclaw:knowledge search`
- Agent RAG 内部调用

写入内容：

- query 文本和过滤条件。
- retrieval mode。
- embedding provider、model、fallback。
- 前 10 个结果的 source、chunk、score、citation 和 snippet。
- 查询错误，包含脱敏后的 provider 错误。

对同一用户快速输入造成的页面搜索，可以只记录防抖后的实际请求，不记录每个键入变化。

### 8.2 命中解释

搜索结果增加 explain 字段：

```ts
interface KnowledgeResultExplanation {
  matchedFields: Array<'title' | 'tags' | 'summary' | 'content' | 'embedding'>;
  keywordHighlights: string[];
  vectorScore?: number;
  keywordScore?: number;
  recencyBoost?: number;
  fallback?: string;
}
```

解释只用于 UI 和调试，不参与排序计算，避免循环依赖。

### 8.3 RAG usage 回放

`knowledge_usage_refs` 保留为引用事实表。Phase 5 新增 API 根据 usage ref 聚合：

- 关联 query log。
- 关联 query results。
- 关联 Agent run 或 session run。
- 展示 citation 是否来自 top results。
- 展示是否发生 keyword fallback。

### 8.4 治理动作生成

`knowledgeGovernanceActionService` 根据现有 insights 生成 open actions：

- duplicate：生成 `merge_duplicate`。
- stale：生成 `reprocess_stale`。
- parser_incomplete：生成 `ignore_parser_incomplete` 或 `review_metadata`。
- empty_index：生成 `rebuild_empty_index`。

治理动作执行后写状态，且重新计算 insights。

### 8.5 知识候选生成

候选生成来源：

1. Session assistant message：用户点击“保存为知识”时，若内容包含决策、约束、风险、经验，生成候选预览再确认。
2. Agent run output：任务完成后，提取 TDD 证据、验证结果、修复结论和 review findings。
3. Workflow artifact：计划、验收、总结 artifact 可生成候选。
4. Task event：finish_branch、verification、acceptance 的关键结论可生成候选。

候选内容必须可编辑，不能自动入库覆盖用户判断。

## 9. API 设计

### 9.1 查询日志

```http
GET /api/knowledge/query-logs?projectId=<projectId>&roomId=<roomId>&actorType=<actorType>&limit=50
GET /api/knowledge/query-logs/:logId
```

详情返回：

- query log。
- 前若干 query results。
- feedback 汇总。
- 关联 usage refs。

### 9.2 反馈

```http
POST /api/knowledge/query-results/:resultId/feedback
```

请求：

```ts
{
  feedback: 'relevant' | 'irrelevant' | 'useful' | 'wrong_scope' | 'stale' | 'missing_context';
  note?: string;
}
```

### 9.3 治理动作

```http
GET /api/knowledge/governance-actions?projectId=<projectId>&status=open
POST /api/knowledge/governance-actions/rebuild
PATCH /api/knowledge/governance-actions/:actionId
```

`PATCH` 支持：

```ts
{
  status: 'ignored' | 'completed';
  note?: string;
}
```

批量动作必须按 project 限界，不允许跨项目修改。

### 9.4 知识候选

```http
GET /api/knowledge/candidates?projectId=<projectId>&status=pending
POST /api/knowledge/candidates
PATCH /api/knowledge/candidates/:candidateId
POST /api/knowledge/candidates/:candidateId/accept
POST /api/knowledge/candidates/:candidateId/reject
```

接受候选时允许编辑 title、content、tags 和 metadataPatch。

## 10. 前端信息架构

`/knowledge` 继续保持左侧范围导航、中间列表、右侧详情的工作台结构，但中间主区增加视图切换：

1. **资源**：当前资源列表、搜索、筛选、导入和详情。
2. **治理**：open governance actions，支持处理、忽略、批量重建和重新处理。
3. **RAG 观测**：query logs、Agent usage refs、fallback、引用回放和结果反馈。
4. **候选**：待确认知识候选，支持接受、编辑、拒绝。
5. **索引**：embedding provider 状态、覆盖率、重建入口和失败 chunks。

第一版可以把视图切换做成中间主区顶部 tabs，不新增路由。右侧详情面板根据当前视图变化：

- 资源视图：显示 source 详情。
- 治理视图：显示 action 详情和影响 source。
- RAG 观测视图：显示 query log、结果列表和 usage refs。
- 候选视图：显示候选原文、建议 metadata 和接受表单。
- 索引视图：显示 provider 状态、source/chunk 覆盖和失败列表。

## 11. 页面交互细节

### 11.1 资源视图

保留现有能力。新增：

- 搜索结果行展示“为什么命中”。
- 结果行支持标记相关或不相关。
- 详情页 refs tab 展示 query log 和 Agent usage。

### 11.2 治理视图

治理项展示：

- action type。
- 来源标题。
- 原因。
- 建议动作。
- 当前状态。

操作：

- duplicate：选择保留 source，其他 source 禁用或删除知识记录。
- stale：重新处理。
- empty_index：重建索引。
- parser_incomplete：忽略或标记等待 sidecar。
- review_metadata：打开 metadata 编辑。

### 11.3 RAG 观测视图

列表维度：

- query。
- actor。
- mode。
- provider/model。
- result count。
- fallback。
- created_at。

详情维度：

- top results。
- ranking explanation。
- citation keys。
- usage refs。
- feedback。

### 11.4 候选视图

候选项展示：

- 来源类型。
- 标题。
- 摘要。
- confidence。
- 建议 tags。
- 建议 key_points、decisions、constraints、risks、learnings。

接受候选时使用现有 manual knowledge import 语义，拒绝候选只改变 candidate 状态，不删除原始消息或 run。

### 11.5 索引视图

在 Phase 4B.1 的 Embedding strip 基础上扩展：

- 按 source 显示 missing/stale/failed chunks。
- 支持 source 级重建。
- 展示最近一次重建结果。
- 展示 provider 不可用原因。

## 12. Agent RAG 可观测规则

Agent 使用知识库工具时必须满足：

1. usage ref 必须记录 query、mode、provider、model、fallback 和 citation key。
2. 如果 Agent 回答中出现 citation key，页面应能跳转到对应 source/chunk。
3. 如果 Agent 回答涉及项目资料但没有任何 usage ref，RAG 观测页应能显示“未使用知识库工具”的诊断。
4. 如果发生 provider failure 并 fallback 到 keyword，必须在 query log 和 usage metadata 中显示。
5. 不把 query logs 当成自动评价结果，人工 feedback 才能改变质量统计。

## 13. 安全与隐私

1. Query log 不保存完整 chunk 原文，只保存短 snippet 和 citation。
2. Embedding provider 错误继续脱敏，不泄露 API key。
3. URL candidate 和 URL source 仍不自动 fetch。
4. Workspace candidate 必须复用 workspace path 校验，禁止 absolute path、traversal、ignored 和 oversized 文件。
5. 候选入库前必须用户确认，避免 Agent 输出被无审核写入项目知识。
6. 治理动作必须按 project/room 限界，不能跨项目修改 source。

## 14. 验收标准

1. 用户在 `/knowledge` 的 RAG 观测视图能看到页面搜索和 Agent RAG 搜索日志。
2. 某条 query log 能展开看到 top results、ranking explanation、citation 和 usage refs。
3. 用户能对搜索结果标记 relevant、irrelevant、wrong_scope、stale 或 missing_context。
4. 治理视图能展示 duplicate、stale、parser incomplete、empty index 对应的 open actions。
5. 用户能对治理 action 执行忽略、重新处理、重建索引或 metadata review。
6. 候选视图能从 session message 或 Agent run 生成候选，并在用户确认后写入知识库。
7. Agent RAG usage metadata 能显示 provider、model、retrieval mode 和 fallback。
8. 未使用知识库工具的 Agent 回答不会被伪造成 RAG 使用记录。
9. 页面在桌面和移动视口无横向溢出，视图切换不会打断当前筛选范围。
10. 后端测试覆盖 query log、feedback、governance actions、candidate accept/reject 和 RAG usage 聚合。

## 15. 风险与缓解

### 15.1 数据量增长

风险：query logs 和 query results 会随着使用增长。

缓解：默认只保留前 10 个结果；增加 limit、分页和后续清理策略；不保存完整 chunk 原文。

### 15.2 用户反馈负担

风险：要求用户标记相关性会增加操作成本。

缓解：反馈是可选动作；只在用户排查检索质量时使用，不打断普通搜索。

### 15.3 治理动作误操作

风险：批量 disable 或 merge duplicate 可能影响已有引用。

缓解：第一版 duplicate merge 只默认禁用重复 source，不删除原始资源；删除仍保留单独确认。

### 15.4 候选知识污染

风险：Agent 输出可能包含错误结论，被接受后污染知识库。

缓解：候选必须用户确认；候选详情显示来源、原文和 confidence；接受时可编辑 metadata。

### 15.5 页面复杂度上升

风险：五个视图会让 `/knowledge` 变成复杂后台。

缓解：继续使用同一工作台结构；默认停留资源视图；治理、RAG 观测、候选、索引作为任务视图，不互相嵌套。

## 16. 推荐推进顺序

Phase 5 建议拆成两个可验收子阶段：

### Phase 5A：RAG 可观测和检索反馈

范围：

1. query log 和 query results。
2. search result explanation。
3. RAG usage 聚合 API。
4. `/knowledge` RAG 观测视图。
5. 结果反馈。

验收重点：用户能回放某次搜索或 Agent RAG 调用，并能判断为什么命中。

### Phase 5B：治理动作和候选知识流

范围：

1. governance actions。
2. 治理视图。
3. candidate 生成、接受、拒绝。
4. source 级重建和重新处理入口。
5. candidate 入库复用现有 manual/session_note 语义。

验收重点：治理信号不再只是提示，用户可以处理；知识沉淀不再只靠手动保存。

Phase 5 完成后，再评估 Phase 6：

- 复杂解析 sidecar provider registry。
